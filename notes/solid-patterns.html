🧩 SOLID Principles & Design Patterns

SOLID principles and design patterns used in real projects.

SOLID Principles

Five principles for writing maintainable, extensible object oriented code. They come up constantly in interviews because they are the vocabulary for explaining why a piece of code is well designed or badly designed.

Single Responsibility Principle (SRP)

A class should have only one reason to change. In practice this means a service class does one job, for example a RiskScoringService should score risk, not also send notifications and not also handle persistence. When a class starts doing three unrelated things, split it.

Open/Closed Principle (OCP)

A class should be open for extension but closed for modification. Instead of adding more if-else branches to an existing method every time a new case shows up, you add a new implementation of an interface. This is usually paired with the Strategy pattern, since new strategies can be added without touching existing strategy classes.

Liskov Substitution Principle (LSP)

A subclass should be usable anywhere its parent class is expected, without breaking behavior. If a subclass overrides a method and throws an exception the parent never threw, or returns something that violates the parent's contract, that is an LSP violation, and it usually means the inheritance relationship was wrong to begin with.

Interface Segregation Principle (ISP)

Clients should not be forced to depend on methods they do not use. Instead of one large interface with ten methods where most implementers only need three, split it into smaller, focused interfaces. This keeps implementing classes clean and avoids empty or throw-not-supported method bodies.

Dependency Inversion Principle (DIP)

High level modules should depend on abstractions, not concrete implementations. A service class should depend on a RiskScoringStrategy interface, not on a specific concrete scoring class. Spring's dependency injection is basically DIP built into the framework, since beans are wired by interface type and the concrete implementation can be swapped without touching the consumer.

Design Patterns Used in Real Projects

Below are the patterns that come up the most often when explaining real project decisions, with the actual scenario they solved.

Strategy Pattern

Used to select an algorithm at runtime based on some condition, instead of branching with if-else. On one project I had risk scoring logic where the scoring algorithm depended on the applicant's credit tier. I defined a RiskScoringStrategy interface with three implementations, one per tier, each a Spring @Component so it gets picked up by component scanning automatically. This satisfies both OCP (new tiers just mean a new implementation class) and DIP (the service depends on the interface).

Factory Pattern

Used to centralize object creation logic so callers do not need to know which concrete class to instantiate. Paired with the strategy example above, a factory class reads the applicant's credit profile, classifies it into a risk category, and returns the matching strategy implementation. This kept the classification logic in exactly one place instead of scattered across every caller.

Singleton Pattern

Ensures only one instance of a class exists. Spring beans are singleton scoped by default, so this pattern is mostly handled by the framework rather than written by hand. The one time it matters explicitly is remembering that a singleton bean must be stateless, meaning no mutable instance fields that hold per-request data, since the same instance is shared across every concurrent request. Request-specific data goes into method parameters or local variables, never instance fields.

Builder Pattern

Used for constructing objects that have many optional fields, so you avoid a constructor with eight parameters where it is easy to mix up the order. Common on DTOs and request objects in a Spring Boot service, especially with Lombok's @Builder generating the boilerplate.

Observer Pattern

Defines a one-to-many dependency so that when one object changes state, dependents get notified. Spring's ApplicationEventPublisher and @EventListener are a built-in implementation of this. I used it to decouple a core write operation from secondary side effects, for example publishing an event after a status update instead of calling the notification logic directly inline, so the core transaction does not need to know who is listening.

Concurrency Related Patterns

These come up more in system design and multithreading discussions than in day to day Spring Boot work, but they are worth knowing by name since they explain the reasoning behind higher-level abstractions like ExecutorService and CompletableFuture.

  • Producer-Consumer, producer threads generate data, consumer threads process it, a shared queue decouples the two. Basis for message queue based processing.
  • Thread Pool, reuses a fixed set of worker threads instead of creating and destroying threads per task, avoiding thread creation overhead. This is what ExecutorService gives you.
  • Futures and Promises, represents the result of an async operation that is not available yet. Java's Future and CompletableFuture are direct implementations.
  • Monitor Object, synchronizes access to shared state so only one thread executes a critical section at a time, preventing race conditions. This is essentially what synchronized blocks give you.
  • Read-Write Lock, allows many concurrent readers but only one writer at a time, useful when reads vastly outnumber writes on a shared resource.
