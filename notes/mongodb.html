🍃 MongoDB

Core concepts, queries, aggregation, and interview questions.

Core concepts

Database    →  container for collections
Collection  →  group of documents (like a table, but schema-less)
Document    →  a single BSON record (like a row, but nested/flexible)
Field       →  key-value pair inside a document
_id         →  primary key, auto-generated ObjectId if not supplied

CRUD basics

// Insert
db.users.insertOne({ name: "Kalyan", role: "dev", age: 28 })
db.users.insertMany([{ name: "A" }, { name: "B" }])

// Read
db.users.find({ role: "dev" })                    // all matching
db.users.findOne({ _id: ObjectId("...") })        // single doc
db.users.find({ age: { $gt: 25 } })               // comparison
db.users.find({}, { name: 1, _id: 0 })            // projection
db.users.find().sort({ age: -1 }).limit(10).skip(20)

// Update
db.users.updateOne({ name: "Kalyan" }, { $set: { role: "senior" } })
db.users.updateMany({ role: "dev" }, { $inc: { age: 1 } })
db.users.replaceOne({ name: "A" }, { name: "A", role: "qa" })
db.users.updateOne({ name: "X" }, { $set: { role: "dev" } }, { upsert: true })

// Delete
db.users.deleteOne({ name: "A" })
db.users.deleteMany({ role: "intern" })

Query operators

Comparison  →  $eq  $ne  $gt  $gte  $lt  $lte  $in  $nin
Logical     →  $and  $or  $not  $nor
Element     →  $exists  $type
Array       →  $all  $elemMatch  $size
Update      →  $set  $unset  $inc  $push  $pull  $addToSet  $rename
Evaluation  →  $regex  $expr  $text
// Array matching: both conditions on the SAME element
db.orders.find({ items: { $elemMatch: { sku: "A1", qty: { $gte: 2 } } } })

// Without $elemMatch, conditions can match different elements
db.orders.find({ "items.sku": "A1", "items.qty": { $gte: 2 } })

Indexes

db.users.createIndex({ email: 1 }, { unique: true })   // 1 = asc, -1 = desc
db.users.createIndex({ role: 1, age: -1 })             // compound
db.users.createIndex({ bio: "text" })                  // text search
db.users.createIndex({ loc: "2dsphere" })              // geospatial
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 })  // TTL
db.users.createIndex({ email: 1 }, { partialFilterExpression: { active: true } })

db.users.getIndexes()
db.users.dropIndex("email_1")
db.users.find({ role: "dev" }).explain("executionStats")
ESR rule for compound index field order: Equality first, then Sort, then Range. A compound index also serves queries on any prefix of its fields, so { role: 1, age: -1 } covers queries on role alone.

Aggregation pipeline

db.orders.aggregate([
  { $match:  { status: "shipped" } },              // filter FIRST (uses index)
  { $group:  { _id: "$customerId",
               total: { $sum: "$amount" },
               count: { $sum: 1 },
               avg:   { $avg: "$amount" } } },
  { $sort:   { total: -1 } },
  { $limit:  10 },
  { $lookup: { from: "customers", localField: "_id",
               foreignField: "_id", as: "customer" } },
  { $unwind: "$customer" },
  { $project:{ name: "$customer.name", total: 1, _id: 0 } }
])
Common stages
$match    →  filter documents (push as early as possible)
$group    →  group and accumulate ($sum, $avg, $min, $max, $push, $addToSet)
$project  →  reshape / include / exclude fields
$sort     →  order results
$limit    →  cap result count
$skip     →  offset for pagination
$unwind   →  flatten an array into one document per element
$lookup   →  left outer join to another collection
$facet    →  run multiple sub-pipelines in one pass

Spring Data MongoDB

@Document(collection = "users")
public class User {
    @Id private String id;
    @Indexed(unique = true) private String email;
    private String role;
    private int age;
}

public interface UserRepository extends MongoRepository<User, String> {
    List<User> findByRole(String role);
    Optional<User> findByEmail(String email);
    List<User> findByAgeGreaterThanAndRole(int age, String role);

    @Query("{ 'age': { $gte: ?0 } }")
    List<User> findOlderThan(int age);
}

// Programmatic queries with MongoTemplate
Query q = new Query(Criteria.where("role").is("dev").and("age").gte(25));
q.with(Sort.by(Sort.Direction.DESC, "age")).limit(10);
List<User> users = mongoTemplate.find(q, User.class);

// Atomic update without read-modify-write
mongoTemplate.updateFirst(
    Query.query(Criteria.where("email").is(email)),
    new Update().inc("loginCount", 1).set("lastLogin", Instant.now()),
    User.class);

MongoDB Code Snippets

Reusable MongoDB snippets, question by question (mirrors the SQL snippets page format).

Q: Create a collection with a JSON Schema validator requiring a name and a unique email.

db.createCollection("student", {
  validator: {
    $jsonSchema: {
      required: ["name", "email"],
      properties: {
        name:  { bsonType: "string" },
        email: { bsonType: "string" }
      }
    }
  }
})
db.student.createIndex({ email: 1 }, { unique: true })

Q: Insert a full document, and insert a document specifying only some fields.

db.student.insertOne({ student_id: 1, name: "kalyan", major: "maths" })
db.student.insertOne({ student_id: 2, name: "prabhas" })

Q: Select all documents, sorted by two fields.

db.student.find().sort({ name: 1, major: -1 })

Q: Limit results to the first N documents.

db.student.find().limit(2)

Q: Filter documents where a field matches one of several values.

db.student.find({ name: { $in: ["kalyan", "prabhas"] } })

Q: Filter documents with a partial text match on a field.

db.student.find({ name: { $regex: "kal", $options: "i" } })

Q: Get the distinct values of a field.

db.employee.distinct("sex")

Q: Update a document's value based on a condition.

db.student.updateOne({ name: "kalyan" }, { $set: { name: "poloji" } })

Q: Delete a document based on a condition.

db.student.deleteOne({ name: "poloji" })

Q: Insert-or-update a document without a race condition when two requests hit the same key at once.

// Requires a unique index on cache_key
db.cache.createIndex({ cache_key: 1 }, { unique: true })

try {
  db.cache.insertOne({ cache_key: key, payload: value, expiresAt: exp })
} catch (e) {
  // E11000 duplicate key — someone else inserted first, update instead
  db.cache.updateOne({ cache_key: key }, { $set: { payload: value, expiresAt: exp } })
}

// Or in one atomic call using upsert (preferred over try/catch above)
db.cache.updateOne(
  { cache_key: key },
  { $set: { payload: value, expiresAt: exp } },
  { upsert: true }
)

Replication & sharding

Replica set  →  1 primary + N secondaries, automatic failover via election
                Writes always go to the primary
                Secondaries replicate from the oplog (capped collection)
                Needs a majority to elect a new primary → use odd member counts

Sharding     →  horizontal partitioning across shards by shard key
                mongos    → query router
                config servers → store cluster metadata
                Shard key choice is effectively permanent and drives distribution

Read & write concerns

Write concern   w:1            → acknowledged by primary only (fast, less safe)
                w:"majority"   → acknowledged by a majority (durable)
                j:true         → wait for journal flush to disk

Read concern    "local"        → whatever the node has (may roll back)
                "majority"     → only majority-committed data
                "linearizable" → strongest, slowest

Read preference primary | primaryPreferred | secondary
                secondaryPreferred | nearest

Top 20 Interview Questions

1. What is MongoDB and how does it differ from a relational database?
MongoDB is a document-oriented NoSQL database that stores data as BSON documents rather than rows in tables. It has no fixed schema, so documents in the same collection can have different fields. It scales horizontally through sharding, favors denormalization and embedding over joins, and while single-document operations are always atomic, multi-document ACID transactions only arrived in version 4.0 and carry more overhead than in a relational database.
2. What is BSON and why not just use JSON?
BSON is Binary JSON, the format MongoDB actually stores and transmits. It supports types JSON has no notion of, like ObjectId, Date, Decimal128, and raw binary. It is also length-prefixed, so the engine can skip over fields it does not need instead of parsing the entire document, which makes traversal significantly faster.
3. What is the _id field and how is an ObjectId built?
Every document has a unique _id that serves as its primary key. If you do not supply one, MongoDB generates a 12-byte ObjectId made of a 4-byte timestamp, a 5-byte random value, and a 3-byte incrementing counter. It is automatically indexed and immutable once written. Because the leading bytes are a timestamp, ObjectIds sort roughly by creation time, which is occasionally useful but should not be relied on for strict ordering across machines.
4. When would you embed a document versus reference it?
Embed when the child data is owned by the parent, always read together, and bounded in size, for example line items inside an order. Reference when the data is shared across many parents, updated independently, or unbounded in growth, for example a user referenced by thousands of comments. The hard constraint is the 16MB document limit, so anything that grows without bound has to be a reference.
5. Why is there a 16MB document size limit?
It prevents a single document from consuming excessive RAM and network bandwidth during a read, since MongoDB loads whole documents rather than individual columns. In practice it is a design signal: if you are approaching it, your schema probably has an unbounded array that should be a separate collection. For genuinely large binary payloads, GridFS splits files into chunks across two collections.
6. How do indexes work in MongoDB and what is a covered query?
Indexes are B-tree structures that let the engine locate documents without a full collection scan. A covered query is one where every field the query needs, both in the filter and the projection, exists in the index, so MongoDB answers it entirely from the index without touching the documents. You can confirm this with explain(), where the winning plan shows an IXSCAN with no FETCH stage.
7. What order should fields go in a compound index?
Follow the ESR rule: equality fields first, then sort fields, then range fields. A compound index also serves any prefix of its fields, so an index on { a: 1, b: 1, c: 1 } supports queries on a, on a + b, and on all three, but not on b alone. Getting the order wrong is the most common cause of an index quietly not being used.
8. What is the aggregation pipeline?
A sequence of stages where each stage transforms the document stream and passes the result to the next, similar to a Unix pipe. It handles grouping, joins, reshaping, and computed fields that a plain find() cannot. The key optimization is putting $match and $limit as early as possible so the pipeline can use indexes and reduce the working set before expensive stages like $group or $lookup run.
9. What does $lookup do and what are its limitations?
$lookup performs a left outer join to another collection in the same database. It is noticeably slower than a relational join because there is no query planner optimizing across collections, and in a sharded cluster the joined collection historically had to be unsharded. It is fine for reporting and enrichment, but if you find yourself reaching for it on every read, the schema probably should have embedded that data instead.
10. What is a replica set and how does failover work?
A replica set is one primary and several secondaries holding copies of the same data. All writes go to the primary and replicate to secondaries via the oplog, a capped collection of operations. If the primary becomes unreachable, the remaining members hold an election and a majority vote promotes a new primary. This is why member counts should be odd, since an even split cannot reach a majority and the set goes read-only.
11. What is sharding and what makes a good shard key?
Sharding partitions a collection horizontally across multiple servers, with mongos routing queries and config servers holding the metadata. A good shard key has high cardinality, even write distribution, and appears in most queries so the router can target a single shard rather than broadcasting. A monotonically increasing key like a timestamp is a classic bad choice because every new write lands on the same shard, creating a hotspot.
12. How do transactions work in MongoDB?
Single-document writes have always been atomic. Multi-document transactions arrived in 4.0 for replica sets and 4.2 for sharded clusters, using a session-scoped API with commit and abort. They provide snapshot isolation but hold locks and consume more resources, and there is a default 60-second runtime limit. The idiomatic advice is to design your schema so that a logical unit of work fits in one document and you rarely need them.
13. What are write concern and read concern?
Write concern controls how many nodes must acknowledge a write before it is considered successful: w:1 is just the primary, w:"majority" guarantees durability across a failover, and j:true additionally waits for the journal to flush to disk. Read concern controls what data you are allowed to see: "local" may return writes that could still roll back, while "majority" only returns majority-committed data. Together they are the main consistency versus latency dial.
14. What is a TTL index and where is it useful?
A TTL index on a date field automatically deletes documents once they exceed a configured age, checked by a background thread roughly every 60 seconds. It is ideal for sessions, verification tokens, cache entries, and event logs. Two caveats: deletion is not instant, so it should not be relied on for security-critical expiry, and the indexed field has to actually be a Date type or the index silently does nothing.
15. What is a capped collection?
A fixed-size collection that behaves like a circular buffer: once it reaches its size limit, the oldest documents are overwritten. It preserves insertion order and supports tailable cursors, which is why the replication oplog itself is a capped collection. Documents in one cannot be deleted individually and cannot grow beyond their original size on update.
16. Does MongoDB have schema validation?
Yes. Since 3.6 you can attach a JSON Schema validator to a collection that enforces required fields, types, and value ranges on insert and update. The validation level can be strict or moderate, and the action can be to error or merely warn. It gives you the safety of a schema where you want it, while still allowing fields to vary elsewhere, which is a middle ground people often do not realize exists.
17. What is WiredTiger and what does it give you?
WiredTiger has been the default storage engine since 3.2. It provides document-level concurrency control rather than the collection-level locking of the old MMAPv1 engine, so concurrent writes to different documents no longer block each other. It also brings compression for both data and indexes, and uses MVCC with checkpoints plus a write-ahead journal for durability.
18. How do you diagnose a slow query?
Start with explain("executionStats") and look at the winning plan. A COLLSCAN stage means no index was used; compare totalDocsExamined against nReturned, since a large gap means the index is not selective enough. The database profiler can log all operations above a latency threshold, and currentOp shows what is running right now. The usual fixes are adding or reordering a compound index, adding a projection so less data crosses the wire, or moving a $match earlier in an aggregation.
19. How do you use MongoDB from Spring Boot?
Through Spring Data MongoDB, which gives you two layers. MongoRepository derives queries from method names like findByRole and needs no implementation, while MongoTemplate handles anything more programmatic, including atomic updates built with the Update builder so you avoid a read-modify-write race. Entities are mapped with @Document and @Id, and @Indexed can declare indexes, though in production most teams prefer to manage indexes explicitly through a migration tool rather than auto-creating them.
20. When would you not choose MongoDB?
When the data is highly relational with many-to-many relationships and queries that join across several entities, since you either denormalize heavily or lean on $lookup, and both fight the model. Also when you need strong multi-entity transactional guarantees as the normal case rather than the exception, or when reporting and ad-hoc analytical SQL is a primary access pattern. A financial ledger is a good example of something better served by a relational database.

Where I'd Apply This From My Own Work

My hands-on production work has been on relational databases (SQL Server, Postgres). These map real problems I actually solved onto how I'd approach the same problem in MongoDB, so the reasoning is grounded in real work rather than a generic answer.

1. Reconciling two structurally different data shapes

Situation: Two valuation engines produced structurally different appraisal data, one with per-feature dollar adjustments, the other with percentage-based adjustments, and several fields had no equivalent on the other side.
Task: Store both without forcing a rigid shape that fit neither well.
Action: We solved it relationally, with nullable columns and a normalizer converting percentages to dollars at write time. In MongoDB I'd model each comp as its own document instead, letting each engine's real shape stand rather than forcing one column set, with schema validation only on the fields both share.
Result: Same underlying principle either way: don't force structurally different data into one rigid shape just because it's conceptually related.

2. A concurrency race writing to the same cache key

Situation: Two parallel calls could hit the same cache key within milliseconds, since neighborhood data got reused across nearby properties, and both could pass a miss check before either had written.
Task: Guarantee only one write wins without a distributed lock adding latency to every request.
Action: We used a unique constraint in Postgres and caught the resulting exception as an expected signal. In MongoDB the same pattern holds: a unique index on the cache key, and the second concurrent insert throws a duplicate key error I'd catch and read back the winning document.
Result: The fix is database-agnostic: let a unique constraint do the concurrency work instead of an application-level lock.

3. Root-causing an N+1-like query pattern

Situation: Chat operations were taking 30 to 60 seconds, traced to cumulative redundant queries across message, attachment, session, and participant lookups, close to a classic N+1 pattern from lazy loaded associations.
Task: Cut the round trips without changing what data was returned.
Action: We merged separate lookups into joined JPQL queries. In MongoDB I'd look at this the other way around: embed the attachment and participant data directly inside the message document, since they are read together every time, which removes the need for a join entirely instead of just optimizing it.
Result: Same goal, different lever: relational favors a better join, document favors embedding what's always read together.

4. A cache key missing a parameter caused silent collisions

Situation: A cache key built from only the parameters I assumed mattered left out a secondary parameter, and two different requests collided on the same key.
Task: Make sure every parameter that affects the response is captured, not just the obvious ones.
Action: I rebuilt the key generator to derive the key programmatically from every parameter reaching the call. In MongoDB, the same discipline applies to compound index design and to document keys: you cannot decide upfront which fields matter for uniqueness, you have to be exhaustive about what actually varies the data.
Result: The underlying lesson is the same regardless of the datastore: exhaustiveness beats intuition when designing a key.

5. Deciding to fully replace rather than diff a small dataset

Situation: Comps had no stable natural key across refreshes, so diffing old versus new on every appraisal refresh risked matching unrelated comps that happened to share an address.
Task: Decide between precise diffing logic or a simpler full replace.
Action: We deleted and reinserted the full comp set every time, relying on cascade delete, since comp counts were small enough that the cost was negligible. In MongoDB this maps directly to replacing an embedded array wholesale on a document update rather than diffing array elements, which avoids the same class of key-matching bug.
Result: For small, no-stable-key collections, replace-the-whole-set is usually simpler and safer than diffing, in either a relational or document model.

6. Config-gating a feature so its infrastructure could be fully removed

Situation: A cache feature's kill switch only gated behavior, not bean creation, so its DataSource was still built eagerly and could fail startup even with the flag off.
Task: Make turning the flag off genuinely remove the dependency, not just skip calling it.
Action: I used ConditionalOnProperty so the bean itself was only created when enabled. The same principle applies to a MongoDB client: if a feature backed by Mongo is meant to be optional, the MongoClient bean itself needs to be conditionally created, not just conditionally used, or a bad connection string still takes down the app.
Result: Think about failure of infrastructure you own, not just the systems you call into, regardless of which database is behind the flag.

7. Freshness that varies independently per data source

Situation: Different cached endpoints from a third party API had genuinely different real-world update cadences, so one combined staleness check would either refresh too eagerly or serve stale data.
Task: Track freshness independently per endpoint rather than with one global rule.
Action: We anchored per-endpoint TTLs to real update cadences at the application level. In MongoDB I'd implement the same idea more natively with a TTL index per collection, or a lastUpdated field checked per document type, so each data source expires on its own schedule instead of a single blanket rule.
Result: Mongo's built-in TTL index would actually simplify this compared to hand-rolled freshness logic.

8. A shared database with another team's production tables

Situation: New cache tables needed to live in a database already shared with another team's production tables, and there was pressure to just run DDL manually to move faster.
Task: Keep the schema reproducible without touching or risking the other team's tables.
Action: I wired the new tables into the existing Flyway migration process instead. The MongoDB equivalent is treating index creation and schema validation rules as versioned, applied through a migration tool or an idempotent startup script, rather than someone running createIndex by hand against a shared cluster.
Result: Whatever the datastore, ad hoc changes against shared infrastructure are the risk, not the specific DDL syntax.

9. Presence data that needed to be shared across instances

Situation: Presence tracking lived in one instance's memory, so a user's online status looked inconsistent depending on which instance handled a given request once we scaled to multiple instances.
Task: Centralize presence so every instance reads the same source of truth.
Action: We moved it to Redis. If I were choosing a document store for this instead, I'd use a capped collection or a TTL-indexed collection in MongoDB, since presence records are short-lived and don't need durability, similar reasoning to why we picked Redis over a relational table here.
Result: The deciding factor was access pattern, not the specific technology, frequent reads and writes on short-lived data.

10. Reusing an ill-fitting schema instead of forking it

Situation: Land appraisals had no ARV, no beds or baths, and no adjustment breakdown, but still needed to live in the same appraisal tables used by residential and commercial.
Task: Decide between forcing land into the existing shape or building a third schema.
Action: We reused the existing tables, leaving unused columns null and documenting why. This is actually the scenario where I'd argue MongoDB is the better original choice: a land document would simply omit the fields that don't apply, with no null columns and no need to justify an ill fit after the fact.
Result: It's a good example of a real limitation of a fixed relational schema that a flexible document model avoids by default.
