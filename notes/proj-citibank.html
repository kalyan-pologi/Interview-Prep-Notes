Project

🏦 Citibank: Digital Banking & Risk Infrastructure Modernization

Role: Java Developer · Domain: Retail & Consumer Banking, Payments, Risk, and Fraud Analytics

Customers expected an instant loan decision, but the existing process took hours and was causing significant drop-offs. We rebuilt this as an event-driven system in Java, Spring Boot, and Kafka, where fraud scoring and credit risk assessment run in parallel instead of one waiting on the other, bringing the end-to-end decision time down to seconds. I worked across the full backend: the application submission APIs, the scoring pipeline, the decision engine, and integrations with external credit bureau APIs.

Flow

When a user submits a loan or credit card application, the request goes through an API Gateway for authentication and routing, then to the Application Service (Spring Boot). This service validates the input, performs an idempotency check to avoid duplicate processing, stores the application in PostgreSQL, and publishes an application.submitted event to Kafka. From here the system shifts from synchronous request handling to asynchronous, event-driven processing.

The event is partitioned by applicationId to guarantee ordering per application and allow horizontal scaling. Two independent consumer groups, Fraud Service and Credit Risk Service, consume the event in parallel, which is critical to meeting a sub-3-second SLA.

The Fraud Service calls external dependencies synchronously, Device Intelligence, an internal blacklist, and a fraud ML model, all wrapped in circuit breakers, retry policies, and rate limiting to prevent cascading failures. Hot behavioral features are cached in Redis for fast access, and the computed fraud score is persisted in PostgreSQL before publishing a fraud.result event.

The Credit Risk Service consumes the same application.submitted event, calls the Credit Bureau API, a customer profile service, and a credit risk ML model, also behind resilience patterns, computes metrics like debt-to-income and probability of default, and publishes a credit.risk.result event.

The Decision Service is the aggregation layer. It consumes both result events, correlates them by applicationId, holds temporary state in Redis, and applies a short time window, for example 2.5 seconds inside the overall 3-second SLA, to wait for both results. If the fraud score comes back high risk, it short-circuits and rejects immediately without waiting on credit risk. If only one result arrives within the window, the case routes to manual review and a decision.timeout event is published. Once a final decision is made, it is stored in the audit database, a final.decision event is published, and the Application Service updates the application status.

For manual review, the Decision Service sends a message to a review queue that business analysts or compliance officers work through in a support portal. Their decision generates a manual.decision.completed event that finalizes the application state.

Observability and regulatory reporting systems consume the same Kafka events asynchronously and outside the real-time decision path, so audit logging and compliance reporting never affect the SLA.

Design Reasoning

The core idea is combining synchronous calls where a result is needed immediately, the ML and bureau calls, with asynchronous Kafka messaging for everything between services. Fraud and credit risk run independently and in parallel rather than sequentially, the Decision Service owns correlation and short time-boxed state, resilience patterns prevent one failing dependency from cascading into the whole pipeline, and manual review is the human-in-the-loop fallback when the system cannot decide confidently within the SLA.

Joining Mid-Development

I joined this project after the core application submission and Kafka pipeline had already been partially built by a developer who had since moved to a different team, with limited documentation. The Decision Service in particular, the most critical piece since it correlates fraud and credit results into the final loan decision, had no handover and no comments explaining the reasoning behind its design. Getting productive quickly meant reading the Kafka topic contracts and tracing actual message flow through logs rather than relying on documentation that did not exist, then writing my own notes as I went so the next person would not be stuck the same way.
