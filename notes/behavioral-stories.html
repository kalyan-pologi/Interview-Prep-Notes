Appraisal

Designing systems so two related but different write paths can never collide

On the appraisal side, we had two ways an appraisal could get saved. If a user paid for a full report, roughly $50 to $100 each, that went into a permanent history table tied to billing, so it had to stay correct forever. Free browsing made up the large majority of traffic, maybe 80 to 90 percent of requests, and that got cached separately so we weren't recomputing valuations on every page view.

Both of these look like the same action, saving an appraisal, so it would've been easy to let them share one code path. With that much free traffic running next to a smaller but high value paid path, even a bug affecting 1 in 1,000 requests could mean a handful of double charges or corrupted audit rows a week, each needing a manual refund plus an investigation into whether other records were affected.

Instead of a shared service with a check for whether it was a paid request, which breaks the moment someone adds logic to one side without thinking about the other, I split the two into completely separate Spring Boot starter modules. Crossing that boundary required adding a new dependency on purpose, not a few careless lines in the wrong place.

The two systems have run side by side since with zero incidents of one leaking into the other, so zero refunds and zero audit corrections tied to this failure mode on a directly revenue generating feature. It also meant new engineers could see the safety boundary from the module structure alone, without needing someone to explain it.

PDF download returning 404 even though the file existed

We had a bug where users would click to view a PDF appraisal report they'd already paid for, and get a 404, even though we could see the file sitting right there in blob storage. This was hitting every download attempt in that environment, so effectively 100 percent failure on a feature customers had already been charged $50 to $100 for, and it was generating support tickets within hours.

The tempting move was to dive into the URL building code, since a 404 on a valid looking URL feels like a string construction bug. Instead I went into the storage console first and manually checked which account the blob actually lived in. Turned out the PDF was uploaded to one storage account, but the code building the download URL pointed at a different, similarly named one. Because we only ever persisted the blob filename and built the signed URL at read time from config plus that filename, the bug surface was tiny once I knew the real location. It came down to a one line config change, not a logic fix at all.

Downloads went back to resolving immediately after deploy, closing the support queue on it the same day. What took me maybe 20 minutes of checking actual runtime state could easily have been half a day of reading through URL construction code that was never broken in the first place. That's the habit I kept, verify where the data actually is before assuming the code that points at it is wrong.

Payment status stuck on Pending despite payment already being deducted

A bug came in where appraisals that had already been paid for were still showing as Pending in the history table, even though the payment transaction id was right there on the record. Every paid appraisal was hitting this, so 100 percent of a revenue generating flow was showing customers the wrong state on something they'd just been charged for. That's the kind of thing that drives support tickets and refund requests not because anything was actually broken financially, but because the UI said it was.

When I traced the status update logic, I found it was unconditionally defaulting to Pending regardless of state. There wasn't a broken condition, there was no condition at all, the paid branch simply didn't exist. I added the check for a payment transaction id and set the status to FormDataReady when it was present. The detail that mattered was making sure that check ran against the same row the payment write had just committed, rather than a fresh read that could land before the write and reintroduce the bug intermittently, which would've been far harder to diagnose the second time.

Status started reflecting reality immediately after deploy, which cut off an entire category of "I paid but it says pending" support contacts. Diagnosis took longer than the fix, maybe an hour of tracing versus a few lines of code, so I was back on my planned sprint work the same day.

Noticing two endpoints were silently not being tracked for billing

While working on something unrelated, I noticed two endpoints, one for land comps and one for plex comps, were computing a result and discarding it, unlike the main appraisal endpoint which recorded every request into the paid history table. These two had probably been live for months that way, so every request through them was billable work with no record of it ever happening.

Nobody had asked me to look at this, but untracked billable requests is a revenue leak and an audit gap, not a style issue. If those endpoints were even doing 10 or 20 requests a day between them, that's potentially hundreds of unrecorded billable events, and no way to reconstruct them after the fact since we weren't writing anything down.

I flagged it to the team first, then brought both endpoints in line with the main appraisal endpoint. The key choice was reusing the existing historyService.saveAppraisal call rather than writing a new save path, because that call already had retry logic and critical log alerting on failure. Writing my own would've meant a second implementation of the same safety behavior to keep in sync forever.

Both endpoints started recording properly, closing the audit gap going forward. The part I'd point to is that matching the existing pattern took less time than inventing a new one and left us with one save path to maintain instead of three.

Land appraisals not fitting an existing schema

We got asked to support land appraisals using the same appraisal and comp tables we already had for residential and commercial. The problem was land data has no ARV, no bedrooms or bathrooms, none of the adjustment breakdown the other two types rely on. Realistically only about a third of the existing columns applied. There was no spec for how a poorly fitting shape should map in, so the call was mine.

I reused the existing tables rather than building a third schema. I mapped the fields that did apply, as-is value and lot size, and left the rest null deliberately, which was already the established pattern since the commercial engine left some residential-only columns null too. The alternative, a dedicated land schema, would've meant a third set of joins in every cross-property-type report and query we had, plus a third migration path going forward, for a property type making up maybe 5 to 10 percent of volume.

Land shipped without forking the schema, so all three property types stayed queryable through one set of tables and no existing report needed rewriting. The tradeoff I made explicit was documenting exactly which columns are intentionally null per property type, because the real cost of this approach isn't the nulls, it's someone six months later reading a null and filing a bug for data that was never supposed to be there.

Choosing a full replace instead of a diffing approach for comps

Every time an appraisal got refreshed, we had to update its list of comparable properties. I had to decide between diffing the old and new comp lists to update only what changed, or wiping the set and reinserting fresh.

Diffing sounds more precise, but comps have no stable key across refreshes. The set can shrink, grow, or completely reorder between runs, so a diff has to infer which old row matches which new one. That inference is exactly where it breaks, two unrelated comps could share an address after a resale and get matched incorrectly, producing a silently wrong adjustment on a billing relevant report.

I went with delete and reinsert. Comp counts were small, typically 5 to 15 per appraisal, so a full replace was maybe a handful of extra row writes, call it single digit milliseconds, versus the ongoing cost of maintaining matching logic that could produce wrong numbers. I leaned on the foreign key's cascade delete from the parent appraisal so the whole replace ran inside one transaction with no chance of orphaned comp rows if something failed partway.

The refresh logic stayed simple enough that nobody has had to touch it since, and we avoided an entire class of data correctness bug on a paid feature. The honest tradeoff is that this only holds while comp counts stay small. If they grew into the hundreds, the math flips and diffing becomes worth the complexity.

Explaining why a cache miss must never be able to trigger a charge

Product stakeholders wanted the free browsing experience to feel fast and seamless, and someone suggested simplifying the backend by letting the free cache path and the paid history path share more logic. The pitch was saving maybe a week or two of engineering time. I needed to explain to a non-technical audience why that wasn't just an engineering preference.

Talking about module boundaries and write paths wasn't going to land, so I framed it entirely around outcomes. Free browsing was 80 to 90 percent of our traffic and paid reports ran $50 to $100 each. If those two shared a write path and a bug slipped through at even a 0.1 percent rate, that's a handful of customers a week either charged for something they never bought, or having their paid report quietly overwritten by someone else's free lookup. Each one is a refund, a support contact, and a customer who now doubts every number we show them.

I put it as a straight comparison: one or two weeks of engineering effort now, versus permanently removing the possibility of wrongly charging a customer, not just making it less likely.

They agreed to keep the separation. What made it work was converting a structural risk into dollars and customer trust, since that's the currency they actually evaluate decisions in. Framed as architecture it reads as engineering preference, framed as refunds it reads as a business decision.

Mashvisor API / Caching Layer

A cache miss ends up racing to write the same row

I was building a caching layer for a report pipeline that fired around 20 parallel API calls, and under load testing I started seeing intermittent constraint violation exceptions, roughly 1 to 2 percent of reports failing outright. Two of those parallel calls could ask for the same neighborhood data within milliseconds of each other, since neighborhood data gets reused across nearby properties, both would find nothing cached, and both would try to insert. A classic race, and each one failed the entire report, not just that one field, on a feature the customer had already paid for.

I looked at a Redis distributed lock first, but that puts latency on every single write to guard against a rare collision, and on a pipeline already making 20 calls I didn't want that on the common path. So I let the database be the arbiter instead. The cache key already had a unique constraint, so the first insert wins and the second gets a constraint violation, which I caught as an expected signal rather than an error, then read back the row the winner had just written. The detail that mattered was running that catch in a fresh transaction, because once JPA hits a constraint violation it marks the whole transaction rollback only, so a retry sharing it would fail too.

That 1 to 2 percent failure rate dropped to effectively zero with no measurable latency added on the normal path and no locking infrastructure to run. Each of those failures had meant a customer charged with no deliverable, so a support ticket and a manual refund or regenerate every time. At our volume that was several of those a week, gone entirely.

Cutting redundant API calls to zero for repeat property lookups

Our reporting pipeline was making around 20 calls to a paid third party real estate API for every single report, even when we'd just looked up that same property or the same neighborhood data minutes earlier. At roughly 2 to 5 cents a call and a few hundred reports a day, that's somewhere around $300 to $800 a month going to data we already had sitting in our database. It also added real latency, since those 20 calls accounted for most of a report's wait time, often 8 to 12 seconds before the user saw anything.

I needed to cut that without touching all 20 call sites individually, since that's 20 chances to introduce an inconsistency and 20 places to maintain forever. So I built the cache as a decorator over the one shared transport interface all those calls funneled through, meaning a single wrapped method covered all 20 endpoints with zero changes at any call site.

The trickier part was freshness. I split it into two independent checks: whether we had the right id to call the endpoint at all, and separately whether the cached data for that id was still fresh. A valid id tells you nothing about whether a specific field is stale, so combining them would've made a stale record indistinguishable from a missing one.

Repeat lookups on fresh data dropped from 20 external calls to zero, cutting that monthly spend by roughly 60 to 70 percent once the cache warmed up, and pulling report generation down into the 2 to 3 second range. And when a single field did go stale, only that one endpoint refetched instead of all 20, so partial staleness cost us one call rather than a full rebuild.

The caching kill switch had no fallback for its own database failing

I built a kill switch for our caching layer using a config flag, the idea being we could turn caching off in seconds if it ever misbehaved in production rather than waiting on a rollback. During review, a teammate asked something I hadn't thought through: what happens if the caching database itself goes down, given the app still created that DataSource at startup?

That was a fair catch, and a meaningful one. Optional at the config level didn't mean optional at the infrastructure level. The DataSource bean was being created eagerly regardless of the flag, so a bad connection string or an unreachable cache database would fail application startup entirely, even with caching switched off. In other words my supposed safety valve had a 100 percent chance of not working in exactly the scenario I built it for, since the service wouldn't even come up to honor the flag.

I fixed it with ConditionalOnProperty so the bean is only instantiated when the flag is true. Flipping it off now genuinely removes the dependency instead of creating the connection and declining to use it.

That turned the kill switch from decorative into actually functional, which matters because it's the difference between a 30 second config change and a full rollback and redeploy, maybe 20 to 30 minutes, during an incident. The lesson I kept is to think about failure in infrastructure I own, not just the systems I call out to.

Adding caching to a pipeline with 20 different call sites

I got asked to add caching to a report pipeline making about 20 different calls to a third party API, spread across several endpoint classes I hadn't written. The obvious approach was to go wrap each call site, but that's 20 separate edits, 20 chances to miss one or implement it slightly differently, and 20 places someone has to remember to update later.

So before writing any caching code I spent maybe half a day tracing how those calls actually flowed. It turned out all 20, regardless of which endpoint class triggered them, funneled through a single shared transport interface with one method. That convergence point was the obvious place to cache, as a decorator around that one method. A decorator is invisible to callers, so nothing at any call site had to change.

I shipped caching across all 20 endpoints with zero changes to existing endpoint classes, which meant zero regression risk in code I didn't write and no review burden on the teams that owned it. It also means any new endpoint added later inherits caching automatically rather than someone needing to remember to wire it up.

The thing I'd highlight is that the half day of tracing is what bought all of that. Had I started at the call sites, I'd have spent several days on a change with 20 times the surface area and worse long term maintainability.

Chat

The 30 to 60 second chat operation slowdown

During UAT, something as basic as sending or deleting a chat message was taking 30 to 60 seconds. Nothing was throwing errors, it was just unusably slow. On a platform where a few hundred chat sessions a day are how brokers, lenders and buyers coordinate on live deals, that's the core feature looking completely broken, and it got flagged as a release blocker that would've slipped the chat launch by at least a sprint.

Rather than guess from reading the JPQL, I turned on Hibernate's SQL logging locally and ran EXPLAIN ANALYZE against a dataset sized like UAT, since query plans look fine on small local data and fall apart as row counts grow. That exposed redundant queries stacking up across message, attachment, session and participant lookups, an N+1 pattern from lazy loaded associations. A single send was triggering somewhere around 15 to 20 database round trips where 3 or 4 would do.

I combined several separate writes into single transactions, merged the redundant lookups into joined queries, and reordered validation so cheap checks like authorization ran before any database call rather than after.

That took the operation from 30 to 60 seconds down to under 2 to 3 seconds, roughly a 95 percent reduction, and we shipped chat on the original date instead of slipping it. Profiling also surfaced correctness bugs hiding behind the slowness, like a delete endpoint returning the wrong status code, which would've gone out silently otherwise.

Reworking transactional boundaries to eliminate a partial write risk

In our message send flow, saving the new message and updating the parent session's last message timestamp were two separate database writes. If anything failed between them, we'd end up with a message that exists but a session that doesn't reflect it, which shows up to users as a conversation that looks empty or stale in the session list even though the message is sitting in the database. On a path handling every single message send, even a 0.1 percent failure rate between those two writes means inconsistent conversations appearing daily.

I wanted both writes atomic without slowing down one of the hottest paths in the system. So I combined the insert and the session update into a single write inside one transaction boundary, which also cut it from two round trips to one.

I added optimistic locking on the session timestamp with a version column, so two near simultaneous sends surface a conflict the caller can retry rather than one silently overwriting the other. I chose optimistic over a pessimistic row lock deliberately, because sends are frequent and short lived, and holding a row lock across the write would serialize unrelated sends to the same session, hurting throughput on a busy conversation for a conflict that's genuinely rare.

The send path came out both faster, fewer round trips, and safer, since partial writes are now structurally impossible rather than just unlikely. It also closed a subtle bug where sessions showed stale last message data under concurrent sends.

Building enquiry sessions when the data model assumed a transaction always existed

We got a request to let a user start a chat with a transaction coordinator before any real estate transaction existed in the system. Commercially this mattered a lot, it's the top of the funnel, someone asking a question before they've committed to a deal, and we were forcing them to email instead. The problem was our entire chat data model, session creation through attachment lookups, assumed a transaction id was always present. The requirement was one line, make chat work without a transaction, and the implications were mine to work out.

Making the column nullable was the easy part and nowhere near sufficient. A nullable column doesn't stop a join or role lookup written against the old assumption from silently returning nothing, which is worse than an error because it looks like working code returning empty results. So I worked through every consumer one at a time, session listing, closing, reopening, attachment lookups, roughly 8 to 10 distinct paths, fixing each place that assumed a transaction existed.

I also had to build new role resolution logic, since the existing logic derived a user's role from the transaction itself, which no longer applied. For enquiry sessions I derived it from the session's own participant records instead.

Enquiry sessions shipped working correctly across every existing chat feature with no special case checks scattered through the codebase. It opened a channel for pre-deal conversations that previously fell back to email, and gave me a repeatable approach: trace every consumer of an assumption before removing it.

Changing an endpoint's status codes without breaking existing consumers

We had an endpoint other services called that always returned a 200 regardless of what actually happened internally. That meant no consumer could distinguish a real failure from success, so failures were being silently treated as successes downstream, which is the kind of thing that corrupts data in systems you don't own and surfaces weeks later as an unexplainable bug.

The initial plan was simply to start returning proper status codes. Partway through I realized the risk: several teams consumed this endpoint, and some likely had logic built around always receiving a 200 with a specific body shape. Changing both the status code and potentially the body would've broken them on deploy, turning my improvement into an incident across multiple teams.

So I adjusted the approach to guarantee the response body never changed shape, only the status code. I scoped a RestControllerAdvice to that one controller using assignableTypes, so consumers parsing the body kept working even if they hadn't updated their status handling yet, and no other controller's error handling was affected by the new advice bean.

We shipped accurate error signaling without a coordinated rollout across every consuming team, so zero downstream breakage and no multi team release coordination, which would've taken weeks to schedule. It wasn't the simpler original plan, but it let each team adopt proper status code handling on their own timeline rather than being forced into it by my deploy.

Notifications

Publishing notifications synchronously blocked message sends under broker slowness

While building our notification pipeline on Kafka, I noticed the message send flow was calling the notification publish step synchronously, inline with the main request. Under load, if the broker got slow, that could add up to 30 seconds to something as simple as sending a chat message. Not everyone on the team initially saw this as worth changing, since in normal conditions the publish returns in milliseconds and the problem is invisible.

Rather than argue it abstractly, I laid out the failure scenario concretely. Kafka doesn't need to go down for this to hurt, it just needs to be briefly slow, which happens during rebalances or broker restarts. In that window, the producer blocking on an ack means every chat send in the system blocks with it. So a secondary system having a routine hiccup takes down the primary feature, and a notification arriving two seconds late gets converted into a message that appears to fail entirely.

I proposed making the publish fire and forget with Async, catching and logging failures inside the async method rather than letting them propagate to the caller, so a broker issue could never surface as a failed send.

We converted it and that coupling disappeared. Chat send latency became independent of broker health, so a Kafka hiccup now costs a slightly delayed notification instead of a 30 second hang on the core user action. The tradeoff we accepted explicitly is that a dropped publish loses that one notification, which is why the logging matters.

Fixing a bean initialization order bug affecting monitoring, not just my feature

While working on notification delivery, I noticed our APM logs had a gap right after startup, maybe the first few seconds of every deploy missing entirely. That had nothing to do with what I was assigned, and nobody had traced it, but startup is exactly when things fail, bad config, unreachable dependencies, failed migrations. We were blind during the single highest risk window of every deploy, on every service, every time.

I dug in and found it was a Spring bean initialization order issue. A log clearing configuration bean was running after the APM appender had already registered, wiping out its earliest output. Spring doesn't guarantee creation order beyond dependency edges you declare explicitly, so these two unrelated beans could initialize in either order, and we'd happened to land on the wrong one.

The fix was small, an explicit DependsOn so the log clearing step runs before the appender registers rather than relying on implicit ordering.

The gap closed, which meant startup failures became diagnosable from logs instead of needing a local reproduction. Concretely that's the difference between reading a stack trace and spending half a day reproducing a deploy time failure. It cost me maybe two hours total and it wasn't my scope, but observability gaps compound quietly, and the next person hitting a startup issue would have burned far more than that.

Choosing Spring's caching abstraction over a hand rolled cache map for notification templates

A teammate had built our notification template lookup on a hand rolled ConcurrentHashMap. My concern was that it reinvented something Spring handles well, and would eventually need the same invalidation logic anyway, just written and maintained by us. They felt the map was simpler and already working, which was fair on its face.

Rather than argue preferences, I walked them through a concrete scenario. The map only loaded on startup and had no eviction path, so a template edit wouldn't appear until a full restart. For notification copy, something product or marketing might tweak, that means every content change requires a deploy, turning a 30 second edit into a release cycle.

I proposed Cacheable and CacheEvict plus an authenticated reload endpoint. The detail that mattered was fanning invalidation across instances over Redis pub sub, because CacheEvict alone only clears the cache on whichever instance received the request. Running multiple instances behind a load balancer, that means some users keep seeing the old template indefinitely, which is arguably worse than everyone consistently seeing stale copy.

We went with the Spring Cache approach. Template changes now propagate across all instances in seconds via an endpoint call instead of requiring a deploy, and we deleted a meaningful chunk of hand written cache management in favour of framework code that's already tested. The disagreement was productive because the concrete failure case did the convincing, not me.
