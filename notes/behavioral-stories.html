Appraisal

What is an appraisal: A professional valuation of a real estate property. It estimates fair market value based on comparable properties, property condition, location, and market data. Used for mortgage lending, refinancing, insurance, and disputes. Residential reports run about 5 pages at 1-5MB, while commercial reports are much larger at roughly 50 pages and 10-30MB. In ReidyAI, we generate these automatically using KNN to select 6 comparable properties and agents to analyze and write the report, charging customers 10 credits (~$4) for residential and 30 credits (~$12) for commercial.

Designing systems so two related but different write paths can never collide

On the appraisal side, we had two ways an appraisal could get saved, and which one you hit depended on the property. We had around 5,000 properties already in our database with cached valuations, and reports on those were genuinely free, zero credits. Anything outside that set cost credits out of a bundle, 50 credits for $20, with residential at 10 credits and commercial at 30. Those paid reports went into a permanent history table tied to billing, so they had to stay correct forever.

Both paths look like the same action, saving an appraisal, so it would've been easy to let them share one code path. But the consequences of a bug differ completely. A free cached lookup leaking into the paid write path means burning a customer's credits for something that should've cost nothing. The reverse means a credit charged report getting silently overwritten by free cache traffic. With the free tier covering 5,000 properties and carrying the large majority of requests, even a bug hitting 1 in 1,000 would mean several credit refunds a week plus an investigation into which audit rows got corrupted.

Instead of a shared service with a check for whether it was a paid request, which breaks the moment someone adds logic to one side without thinking about the other, I split the two into completely separate Spring Boot starter modules. Crossing that boundary required adding a new dependency on purpose, not a few careless lines in the wrong place.

The two systems have run side by side since with zero incidents of one leaking into the other, so zero refunds and zero audit corrections tied to this failure mode on a directly revenue generating feature. It also meant new engineers could see the safety boundary from the module structure alone, without needing someone to explain it.

PDF download returning 404 even though the file existed

We had a bug where users would click to view a PDF appraisal report they'd already spent credits on, and get a 404, even though we could see the file sitting right there in blob storage. These aren't small files either, a residential report runs about 5 pages at 1 to 5MB, and a commercial one is closer to 50 pages at 10 to 30MB, all stored in a blob container. This was hitting every download attempt in that environment, so 100 percent failure on a report a customer had already been charged 10 to 30 credits for, and it generated support tickets within hours.

The tempting move was to dive into the URL building code, since a 404 on a valid looking URL feels like a string construction bug. Instead I went into the storage console first and manually checked which account the blob actually lived in. Turned out the PDF was uploaded to one storage account, but the code building the download URL pointed at a different, similarly named one. Because we only ever persisted the blob filename and built the signed URL at read time from config plus that filename, the bug surface was tiny once I knew the real location. It came down to a one line config change, not a logic fix at all.

Downloads went back to resolving immediately after deploy, closing the support queue on it the same day. What took me maybe 20 minutes of checking actual runtime state could easily have been half a day of reading through URL construction code that was never broken in the first place. That's the habit I kept, verify where the data actually is before assuming the code that points at it is wrong.

Payment status stuck on Pending despite payment already being deducted

A bug came in where appraisals that had already been paid for were still showing as Pending in the history table, even though the payment transaction id was right there on the record. Every paid appraisal was hitting this, so 100 percent of a revenue generating flow was showing customers the wrong state on something they'd just been charged for. That's the kind of thing that drives support tickets and refund requests not because anything was actually broken financially, but because the UI said it was.

When I traced the status update logic, I found it was unconditionally defaulting to Pending regardless of state. There wasn't a broken condition, there was no condition at all, the paid branch simply didn't exist. I added the check for a payment transaction id and set the status to FormDataReady when it was present. The detail that mattered was making sure that check ran against the same row the payment write had just committed, rather than a fresh read that could land before the write and reintroduce the bug intermittently, which would've been far harder to diagnose the second time.

I also added a transaction flush before the status read to ensure the payment write was durable before checking it, preventing a race where a concurrent read might not see the transaction id yet. That's the kind of ordering detail that separates a fix that works 99 percent of the time from one that works consistently.

Status started reflecting reality immediately after deploy, which cut off an entire category of "I paid but it says pending" support contacts. Diagnosis took longer than the fix, maybe an hour of tracing versus a few lines of code, so I was back on my planned sprint work the same day.

Noticing two endpoints were silently not being tracked for billing

While working on something unrelated, I noticed two endpoints, one for land comps and one for plex comps, were computing a result and discarding it, unlike the main appraisal endpoint which recorded every request into the paid history table. These two had probably been live for months that way, so every request through them was billable work with no record of it ever happening.

Nobody had asked me to look at this, but untracked billable requests is a revenue leak and an audit gap, not a style issue. If those endpoints were even doing 10 or 20 requests a day between them, that's potentially hundreds of unrecorded billable events, and no way to reconstruct them after the fact since we weren't writing anything down. I checked the logs and found they were actually getting hit consistently, roughly 5 to 8 times daily combined, which meant we were silently dropping 150 to 240 billable requests every month.

I flagged it to the team first, then brought both endpoints in line with the main appraisal endpoint. The key choice was reusing the existing historyService.saveAppraisal call rather than writing a new save path, because that call already had retry logic and critical log alerting on failure. Writing my own would've meant a second implementation of the same safety behavior to keep in sync forever.

Both endpoints started recording properly, closing the audit gap going forward. The part I'd point to is that matching the existing pattern took less time than inventing a new one and left us with one save path to maintain instead of three, plus it meant any future improvements to the primary save logic automatically benefited all endpoints.

Land appraisals not fitting an existing schema

We supported a fair range of property types, residential, commercial, land, multiplex, duplex and triplex, and we got asked to add land using the same appraisal and comp tables. The problem was land has no ARV, no bedrooms or bathrooms, none of the adjustment breakdown the other types rely on, since there's no structure to compare. Realistically only about a third of the existing columns applied. There was no spec for how a poorly fitting shape should map in, so the call was mine.

I reused the existing tables rather than building a separate land schema. I mapped the fields that did apply, as-is value and lot size, and left the rest null deliberately, which was already the established pattern since the commercial engine left some residential-only columns null too. A dedicated land schema would've meant another set of joins in every cross-property-type report and query, plus another migration path forever, for a property type making up maybe 5 to 10 percent of volume.

Land shipped without forking the schema, so all six property types stayed queryable through one set of tables and no existing report needed rewriting. The tradeoff I made explicit was documenting exactly which columns are intentionally null per property type, because the real cost here isn't the nulls, it's someone six months later reading a null and filing a bug for data that was never supposed to be there.

Choosing a full replace instead of a diffing approach for comps

Our report generation runs a KNN model to pick the 6 most comparable properties to the subject, then does weighted and adjusted calculations across those to land on a value. Every time an appraisal got refreshed, that comp set had to be updated in the database, and I had to decide between diffing the old and new lists to update only what changed, or wiping the set and reinserting fresh.

Diffing sounds more precise, but comps have no stable key across refreshes. KNN can return a completely different 6 depending on what data has changed, so the set can shrink, grow or reorder entirely between runs, meaning a diff has to infer which old row matches which new one. That inference is exactly where it breaks, two unrelated comps could share an address after a resale and get matched incorrectly, producing a silently wrong adjustment on a report a customer paid credits for.

I went with delete and reinsert. We're talking about 6 comps per appraisal, so a full replace is a handful of row writes, single digit milliseconds, versus the ongoing cost of maintaining matching logic that can produce wrong numbers. I leaned on the foreign key's cascade delete from the parent appraisal so the whole replace ran inside one transaction with no chance of orphaned comp rows if something failed partway.

I also added a version check on the parent appraisal to catch cases where two concurrent refresh requests might both read the same old comp set and try to replace it simultaneously. The version bump ensures only one refresh applies, while the other gets a stale update exception and retries, getting the freshest data instead.

The refresh logic stayed simple enough that nobody has had to touch it since, and we avoided an entire class of data correctness bug on a credit charged feature. The honest tradeoff is that this only holds while the comp count stays at 6. If we ever moved to selecting hundreds, the math flips and diffing becomes worth the complexity.

Explaining why a cache miss must never be able to trigger a charge

Product stakeholders wanted the free browsing experience to feel fast and seamless, and someone suggested simplifying the backend by letting the free cache path and the paid history path share more logic. The pitch was saving maybe a week or two of engineering time. I needed to explain to a non-technical audience why that wasn't just an engineering preference.

Talking about module boundaries and write paths wasn't going to land, so I framed it entirely around outcomes. We had roughly 5,000 properties cached in our database that were free to report on, zero credits, and everything outside that set cost 10 credits for residential or 30 for commercial. If those two paths shared a write path and a bug slipped through at even a 0.1 percent rate, it breaks in both directions: a customer viewing a free property gets credits burned for something that should've cost nothing, or a report someone paid credits for gets silently overwritten by an unrelated free lookup. Either way that's a credit refund, a support contact, and a customer who now doubts every number we show them.

I put it as a straight comparison: one or two weeks of engineering effort now, versus permanently removing the possibility of wrongly burning a customer's credits, not just making it less likely.

They agreed to keep the separation. What made it work was converting a structural risk into dollars and customer trust, since that's the currency they actually evaluate decisions in. Framed as architecture it reads as engineering preference, framed as refunds it reads as a business decision.

Mashvisor API / Caching Layer

What is Mashvisor: A third-party real estate data API providing rental market analytics and investment metrics. The rentability tab displays rent estimates, cash-on-cash return, and short-term/long-term rental comps, all powered by Mashvisor. Each API call costs 2-5 cents, and the system makes about 20 parallel calls per property view. Without caching, this adds significant latency (8-12 seconds) and costs roughly $300-800 monthly. The caching layer sits between our app and Mashvisor, reducing redundant calls while managing freshness tradeoffs since different metrics (rent estimates vs comps) age at different rates.

A cache miss ends up racing to write the same row

I was building a caching layer over Mashvisor, the third party API behind our rentability tab, which shows rent estimates, cash on cash return, and short and long term rental comps when a user opens a property. Loading that tab fired around 20 parallel API calls, and under load testing I started seeing intermittent constraint violation exceptions, roughly 1 to 2 percent of loads failing outright. Two parallel calls could ask for the same neighborhood data within milliseconds, since neighborhood metrics get reused across nearby properties, both would find nothing cached, and both would try to insert. A classic race, and each one failed the whole tab rather than one metric.

I looked at a Redis distributed lock first, but that puts latency on every single write to guard against a rare collision, and on a pipeline already making 20 calls I didn't want that on the common path. So I let the database be the arbiter instead. The cache key already had a unique constraint, so the first insert wins and the second gets a constraint violation, which I caught as an expected signal rather than an error, then read back the row the winner had just written. The detail that mattered was running that catch in a fresh transaction, because once JPA hits a constraint violation it marks the whole transaction rollback only, so a retry sharing it would fail too.

That 1 to 2 percent failure rate dropped to effectively zero with no measurable latency added on the normal path and no locking infrastructure to run. Before the fix, those failures meant a user opening a property and seeing the rentability tab simply error out, which on a platform where investors are evaluating deals is the data they came for. At our volume that was a steady trickle of broken page loads a week, gone entirely.

Cutting redundant API calls to zero for repeat property lookups

Our rentability tab, the one showing rent estimates, cash on cash return, and short and long term rental comps for a property, was making around 20 calls to Mashvisor every single time someone opened it, even when we'd pulled that same property or neighborhood minutes earlier. At roughly 2 to 5 cents a call and a few hundred property views a day, that's somewhere around $300 to $800 a month going to data already sitting in our database. It also added real latency, since those 20 calls were most of the tab's load time, often 8 to 12 seconds before an investor saw any numbers.

I needed to cut that without touching all 20 call sites individually, since that's 20 chances to introduce an inconsistency and 20 places to maintain forever. So I built the cache as a decorator over the one shared transport interface all those calls funneled through, meaning a single wrapped method covered all 20 endpoints with zero changes at any call site.

The trickier part was freshness, because these metrics don't age at the same rate. Rent estimates move slowly, rental comps turn over faster. So I split it into two independent checks: whether we had the right id to call the endpoint at all, and separately whether the cached data for that id was still fresh. A valid id tells you nothing about whether a specific metric is stale, so combining them would've made a stale record indistinguishable from a missing one.

I also had to handle partial failures where some endpoints returned fresh data while others were stale, rather than an all-or-nothing rebuild. That meant tracking staleness per endpoint in Redis and invalidating only the metrics that actually needed refresh, not orphaning good data just because one related metric turned stale.

Repeat views on fresh data dropped from 20 external calls to zero, cutting that monthly spend by roughly 60 to 70 percent once the cache warmed up, and pulling tab load down into the 2 to 3 second range. When one metric did go stale, only that endpoint refetched instead of all 20, so partial staleness cost one call rather than a full rebuild. That architectural choice meant the cache paid for itself within a few weeks through pure API savings.

The caching kill switch had no fallback for its own database failing

I built a kill switch for our caching layer using a config flag, the idea being we could turn caching off in seconds if it ever misbehaved in production rather than waiting on a rollback. During review, a teammate asked something I hadn't thought through: what happens if the caching database itself goes down, given the app still created that DataSource at startup?

That was a fair catch, and a meaningful one. Optional at the config level didn't mean optional at the infrastructure level. The DataSource bean was being created eagerly regardless of the flag, so a bad connection string or an unreachable cache database would fail application startup entirely, even with caching switched off. In other words my supposed safety valve had a 100 percent chance of not working in exactly the scenario I built it for, since the service wouldn't even come up to honor the flag.

I fixed it with ConditionalOnProperty so the bean is only instantiated when the flag is true. Flipping it off now genuinely removes the dependency instead of creating the connection and declining to use it. I also added a connection test at startup with a timeout, so if the cache database was reachable but degraded it would fail fast instead of hanging the boot sequence.

That turned the kill switch from decorative into actually functional, which matters because it's the difference between a 30 second config change and a full rollback and redeploy, maybe 20 to 30 minutes, during an incident. The lesson I kept is to think about failure in infrastructure I own, not just the systems I call out to, especially when building safety mechanisms that will only be used during someone's worst day.

Adding caching to a pipeline with 20 different call sites

I got asked to add caching to the Mashvisor integration behind our rentability tab, which made about 20 different calls spread across several endpoint classes I hadn't written. The obvious approach was to go wrap each call site, but that's 20 separate edits, 20 chances to miss one or implement it slightly differently, and 20 places someone has to remember to update later.

So before writing any caching code I spent maybe half a day tracing how those calls actually flowed. It turned out all 20, regardless of which endpoint class triggered them, funneled through a single shared transport interface with one method. That convergence point was the obvious place to cache, as a decorator around that one method. A decorator is invisible to callers, so nothing at any call site had to change.

The implementation used Spring's Cacheable annotation with a composite key builder that handled the varying parameter shapes across endpoints, so each unique call combination got its own cache bucket. I also added cache warming logic to preload neighborhood data on startup, since that's the highest cardinality data and benefits most from being hot before the first user request.

I shipped caching across all 20 endpoints with zero changes to existing endpoint classes, which meant zero regression risk in code I didn't write and no review burden on the teams that owned it. It also means any new endpoint added later inherits caching automatically rather than someone needing to remember to wire it up.

The thing I'd highlight is that the half day of tracing is what bought all of that. Had I started at the call sites, I'd have spent several days on a change with 20 times the surface area and worse long term maintainability, plus I'd have ended up maintaining 20 separate cache implementations instead of one.

Chat

What is Chat: A real-time messaging platform where brokers, lenders, buyers, and transaction coordinators coordinate on live real estate deals. Users can send and delete messages, attach documents, create sessions tied to transactions, and manage participants with different roles. Sessions persist full conversation history, support concurrent sends, and include features like enquiry sessions that can exist before a formal transaction starts. Performance is critical since users expect sub-second send operations, and any slowdown (30-60 seconds) breaks the core feature and kills deals.

The 30 to 60 second chat operation slowdown

During UAT, something as basic as sending or deleting a chat message was taking 30 to 60 seconds. Nothing was throwing errors, it was just unusably slow. On a platform where a few hundred chat sessions a day are how brokers, lenders and buyers coordinate on live deals, that's the core feature looking completely broken, and it got flagged as a release blocker that would've slipped the chat launch by at least a sprint.

Rather than guess from reading the JPQL, I turned on Hibernate's SQL logging locally and ran EXPLAIN ANALYZE against a dataset sized like UAT, since query plans look fine on small local data and fall apart as row counts grow. That exposed redundant queries stacking up across message, attachment, session and participant lookups, an N+1 pattern from lazy loaded associations. A single send was triggering somewhere around 15 to 20 database round trips where 3 or 4 would do.

I combined several separate writes into single transactions, merged the redundant lookups into joined queries, and reordered validation so cheap checks like authorization ran before any database call rather than after.

That took the operation from 30 to 60 seconds down to under 2 to 3 seconds, roughly a 95 percent reduction, and we shipped chat on the original date instead of slipping it. Profiling also surfaced correctness bugs hiding behind the slowness, like a delete endpoint returning the wrong status code, which would've gone out silently otherwise.

Reworking transactional boundaries to eliminate a partial write risk

In our message send flow, saving the new message and updating the parent session's last message timestamp were two separate database writes. If anything failed between them, we'd end up with a message that exists but a session that doesn't reflect it, which shows up to users as a conversation that looks empty or stale in the session list even though the message is sitting in the database. On a path handling every single message send, even a 0.1 percent failure rate between those two writes means inconsistent conversations appearing daily.

I wanted both writes atomic without slowing down one of the hottest paths in the system. So I combined the insert and the session update into a single write inside one transaction boundary, which also cut it from two round trips to one.

I added optimistic locking on the session timestamp with a version column, so two near simultaneous sends surface a conflict the caller can retry rather than one silently overwriting the other. I chose optimistic over a pessimistic row lock deliberately, because sends are frequent and short lived, and holding a row lock across the write would serialize unrelated sends to the same session, hurting throughput on a busy conversation for a conflict that's genuinely rare.

The send path came out both faster, fewer round trips, and safer, since partial writes are now structurally impossible rather than just unlikely. It also closed a subtle bug where sessions showed stale last message data under concurrent sends.

Building enquiry sessions when the data model assumed a transaction always existed

We got a request to let a user start a chat with a transaction coordinator before any real estate transaction existed in the system. Commercially this mattered a lot, it's the top of the funnel, someone asking a question before they've committed to a deal, and we were forcing them to email instead. The problem was our entire chat data model, session creation through attachment lookups, assumed a transaction id was always present. The requirement was one line, make chat work without a transaction, and the implications were mine to work out.

Making the column nullable was the easy part and nowhere near sufficient. A nullable column doesn't stop a join or role lookup written against the old assumption from silently returning nothing, which is worse than an error because it looks like working code returning empty results. So I worked through every consumer one at a time, session listing, closing, reopening, attachment lookups, roughly 8 to 10 distinct paths, fixing each place that assumed a transaction existed.

I also had to build new role resolution logic, since the existing logic derived a user's role from the transaction itself, which no longer applied. For enquiry sessions I derived it from the session's own participant records instead.

Enquiry sessions shipped working correctly across every existing chat feature with no special case checks scattered through the codebase. It opened a channel for pre-deal conversations that previously fell back to email, and gave me a repeatable approach: trace every consumer of an assumption before removing it.

Changing an endpoint's status codes without breaking existing consumers

We had an endpoint other services called that always returned a 200 regardless of what actually happened internally. That meant no consumer could distinguish a real failure from success, so failures were being silently treated as successes downstream, which is the kind of thing that corrupts data in systems you don't own and surfaces weeks later as an unexplainable bug.

The initial plan was simply to start returning proper status codes. Partway through I realized the risk: several teams consumed this endpoint, and some likely had logic built around always receiving a 200 with a specific body shape. Changing both the status code and potentially the body would've broken them on deploy, turning my improvement into an incident across multiple teams.

So I adjusted the approach to guarantee the response body never changed shape, only the status code. I scoped a RestControllerAdvice to that one controller using assignableTypes, so consumers parsing the body kept working even if they hadn't updated their status handling yet, and no other controller's error handling was affected by the new advice bean.

We shipped accurate error signaling without a coordinated rollout across every consuming team, so zero downstream breakage and no multi team release coordination, which would've taken weeks to schedule. It wasn't the simpler original plan, but it let each team adopt proper status code handling on their own timeline rather than being forced into it by my deploy.

Notifications

What are Notifications: An asynchronous messaging system handling 164+ notification types across brokers, lenders, buyers, and transaction coordinators. Built on Azure Service Bus with command-style messaging and delivery guarantees, notifications cover events like signup, document submission, and account approval. Each notification can be delivered via Email, SMS, or In-App, with templates stored in the database (not code) and loaded into Redis at startup. Templates are edited without deploys, invalidated across all instances via Redis pub-sub, and failures are captured via Service Bus dead lettering for replay and audit.

Publishing notifications synchronously blocked message sends under broker slowness

Our notification pipeline runs on Azure Service Bus topics and handles 164 plus notification types across brokers, lenders, buyers and transaction coordinators, fanning out to Email, SMS and In-App. While building it I noticed the message send flow was calling the publish step synchronously, inline with the main request. Under load, if the broker got slow, that could add up to 30 seconds to something as simple as sending a chat message. Not everyone initially saw this as worth changing, since in normal conditions a publish returns in milliseconds and the problem is invisible.

Rather than argue it abstractly, I laid out the failure scenario concretely. The broker doesn't need to go down for this to hurt, it just needs to be briefly slow, which happens during throttling or a transient connectivity blip. In that window, the producer blocking on an ack means every chat send in the system blocks with it. So a secondary system having a routine hiccup takes down the primary feature, and a notification arriving two seconds late gets converted into a message that appears to fail entirely.

I proposed making the publish fire and forget with Async, catching and logging failures inside the async method rather than letting them propagate to the caller, so a messaging issue could never surface as a failed send.

We converted it and that coupling disappeared. Chat send latency became independent of broker health, so a Service Bus hiccup now costs a slightly delayed notification instead of a 30 second hang on the core user action. The tradeoff we accepted explicitly is that a dropped publish loses that one notification, which is why the logging matters, though Service Bus dead lettering covers failures once the message is actually accepted.

Fixing a bean initialization order bug affecting monitoring, not just my feature

While working on notification delivery, I noticed our APM logs had a gap right after startup, maybe the first few seconds of every deploy missing entirely. That had nothing to do with what I was assigned, and nobody had traced it, but startup is exactly when things fail, bad config, unreachable dependencies, failed migrations. We were blind during the single highest risk window of every deploy, on every service, every time.

I dug in and found it was a Spring bean initialization order issue. A log clearing configuration bean was running after the APM appender had already registered, wiping out its earliest output. Spring doesn't guarantee creation order beyond dependency edges you declare explicitly, so these two unrelated beans could initialize in either order, and we'd happened to land on the wrong one.

The fix was small, an explicit DependsOn so the log clearing step runs before the appender registers rather than relying on implicit ordering. I also added a startup listener that logged a timestamp and version info immediately on boot, so even in the gap before APM was ready we had a reference point in all our infrastructure logs.

The gap closed, which meant startup failures became diagnosable from logs instead of needing a local reproduction. Concretely that's the difference between reading a stack trace and spending half a day reproducing a deploy time failure. It cost me maybe two hours total and it wasn't my scope, but observability gaps compound quietly, and the next person hitting a startup issue would have burned far more than that. These kinds of cross cutting concerns are easy to deprioritize, but they're also the ones that multiply your debugging time across every engineer on the team.

Keeping 164+ notification templates editable without a code deploy

We had 164 plus notification types across brokers, lenders, buyers and transaction coordinators, covering everything from signup to financial documents being submitted to an account getting approved, each deliverable over Email, SMS or In-App. The important design decision was that none of that message content lives in code. It's all stored in the database and loaded into Redis at startup, so the app fetches templates on the fly and changing wording means a database update, not a code change.

The part I pushed on was invalidation. A teammate had the lookup on a hand rolled in memory map, which loaded once at startup and had no eviction path at all. That meant any template edit was invisible until a full restart, so a one word copy fix on any of those 150 types required a deploy, turning a 30 second change into a release cycle.

Rather than argue it as preference, I walked through the multi instance case, which is where it really falls apart. Even adding eviction, clearing the cache on the instance that received the request leaves every other instance behind the load balancer serving old copy indefinitely. So some users see the new message and some see the old one, which is worse than everyone consistently seeing stale text. I proposed Spring's Cacheable and CacheEvict with an authenticated reload endpoint that fans invalidation to all instances over Redis pub sub.

I also added an expiry based fallback so templates cached for more than 24 hours auto invalidate and reload even without an explicit evict, preventing the scenario where we forget to trigger the reload and stale copy gets served until the next deploy. That's the kind of defense in depth that prevents typos from turning into outages.

Template changes now propagate across every instance in seconds from a database edit, with no deploy, across all 164 plus types. We also deleted a chunk of hand written cache management in favour of framework code that's already tested, reducing the surface area for bugs and making new engineers faster to productive since they didn't have to learn our custom invalidation pattern.
