Appraisal

What is an appraisal: A professional valuation of a real estate property. It estimates fair market value based on comparable properties, property condition, location, and market data. Used for mortgage lending, refinancing, insurance, and disputes. Residential reports run about 5 pages at 1-5MB, while commercial reports are much larger at roughly 50 pages and 10-30MB. In ReidyAI, we generate these automatically using KNN to select 6 comparable properties and agents to analyze and write the report, charging customers 10 credits (~$4) for residential and 30 credits (~$12) for commercial.

Keeping free and paid reports completely separate so they never mix up

We had two ways to save appraisals. About 5,000 properties were free to report on, zero cost. Everything else charged credits, 10 for residential and 30 for commercial. Both looked like the same save operation to a user, so the natural instinct was to use the same code for both and just add a check inside.

But I thought about what happens if a bug mixes them up. If a customer browsing free properties somehow gets charged, that's money lost and they get angry. If a paid report someone paid for gets overwritten by free data, we have to refund them and spend time figuring out what went wrong. Even a small bug rate like 1 in 1,000 means a few refunds every week and a lot of wasted time investigating.

So instead of a shared service with an isPaid flag check, I split them into two separate Spring Boot starter modules. Crossing that boundary means adding a new dependency on purpose. You can't accidentally slip in a line of code that mixes up the two write paths, and you can't forget about it when adding features later.

Since then, zero incidents of one leaking into the other. Zero refunds from this bug. Zero corrupted audit rows. New engineers see the boundary from the module structure alone, no explanation needed.

PDF download returning 404 even though the file existed

Users were clicking to view a PDF report they'd already paid credits for, and getting a 404. But we could see the file sitting right there in blob storage. Every single download in that environment was failing, so 100 percent broken on something a customer had just been charged 10 to 30 credits for. Support tickets started coming in within hours.

The easy thing would have been to jump into the URL building code. A 404 on a URL that looks fine usually means something went wrong while putting that string together. But instead I opened the storage console and checked by hand which account the file was actually in.

Turns out the PDF was uploaded to one storage account, but the code building the download URL was pointing at a different one with a very similar name. Since we only persisted the blob filename and generated the signed URL at read time from config plus that filename, the bug surface was tiny once I knew the real location. It came down to one line of config. No logic was broken at all.

Downloads resolved again right after deploy and the support queue cleared the same day. Checking the actual runtime state took me maybe 20 minutes. Reading through URL construction code that was never broken could easily have eaten half a day. That's the habit I kept, verify where the data actually is before assuming the code pointing at it is wrong.

Payment status stuck on Pending even though the payment went through

A bug came in where appraisals people had already paid for were still showing as Pending. The payment id was right there on the record, so the money had clearly been taken. Every paid appraisal was hitting this. So on a flow that directly makes us money, we were telling customers the wrong thing about something they'd just been charged for. Nothing was actually broken with the money, but the screen said it was, and that's enough to get people asking for refunds.

When I traced through the status update logic, I found it was unconditionally defaulting to Pending regardless of state. There wasn't a broken condition I had to fix. There was no condition at all. The paid branch simply didn't exist.

So I added the check for the payment transaction id and set the status to FormDataReady when it was present. The part I had to be careful about was making sure that check ran against the same row the payment write had just committed, not a fresh read that could land before the write. If I got that wrong, the bug comes back intermittently instead of always, and intermittent is much harder to diagnose the second time.

Status started showing correctly right after deploy, which killed off all the "I paid but it says pending" messages coming into support. Finding it took about an hour. The fix was a few lines. I was back on my sprint work the same day.

Spotting two endpoints that weren't recording anything for billing

I was working on something unrelated and noticed two endpoints, one for land comps and one for plex comps, were doing all the work to calculate a result and then just throwing it away. The main appraisal endpoint saved every request into the history table we bill off. These two saved nothing. They'd probably been live like that for months, so every request going through them was work we should have been charging for with no record it ever happened.

Nobody asked me to look at this, but requests we can't account for means money we're not collecting and no way to answer questions later if someone asks. I checked the logs and they were getting hit about 5 to 8 times a day between them, so somewhere around 150 to 240 requests a month we had no record of. And there's no way to go back and reconstruct them, because we weren't writing anything down.

I flagged it to the team first, then brought both endpoints in line with the main one. The choice I'd point to is that I reused the existing historyService.saveAppraisal call instead of writing a new save path. That call already had retry logic and critical log alerting on failure. Writing my own would have meant a second implementation of the same safety behavior to keep in sync forever.

Both started recording properly after that, which closed the audit gap going forward. Matching the existing pattern took less time than inventing a new one, and it left us with one save path to maintain instead of three.

Land appraisals didn't fit the tables we already had

We supported six property types, residential, commercial, land, multiplex, duplex and triplex. We got asked to add land using the same appraisal and comp tables we already had. The problem is land has no ARV, no bedrooms or bathrooms, none of the adjustment breakdown the other types depend on, because there's no structure to compare. Realistically only about a third of the existing columns applied. Nobody gave me a spec for how a shape that fits this badly should map in, so the call was mine.

I reused the existing tables instead of building a separate land schema. I mapped the fields that did apply, as-is value and lot size, and left the rest null on purpose. That was already the established pattern, since the commercial engine left some residential-only columns null too.

A dedicated land schema would have meant another set of joins in every cross-property-type report and query, plus another migration path to maintain forever. And land was only about 5 to 10 percent of volume, so that cost wasn't worth paying.

Land shipped without forking the schema. All six types stayed queryable through one set of tables and no existing report needed rewriting. The tradeoff I made explicit was documenting exactly which columns are intentionally null per property type. The real cost isn't the nulls, it's someone six months later reading one and filing a bug for data that was never supposed to be there.

Replacing all the comps instead of figuring out which ones changed

Our report generation runs a KNN model to pick the 6 most comparable properties to the subject, then does weighted and adjusted calculations across those to land on a value. Every time an appraisal got refreshed, that comp set had to be updated in the database. I had to pick between diffing the old and new lists and only updating what changed, or deleting the set and reinserting fresh.

Diffing sounds more precise, but comps have no stable natural key across refreshes. KNN can return a completely different 6 depending on what data changed, so the set can shrink, grow or reorder between runs. That means a diff has to infer which old row matches which new one. That inference is exactly where it breaks. Two unrelated comps could share an address after a resale, get matched incorrectly, and silently produce a wrong adjustment on a report a customer paid credits for.

So I went with delete and reinsert. It's 6 comps per appraisal, so a full replace is single digit milliseconds. That's nothing against the ongoing cost of maintaining matching logic that can produce wrong numbers. I leaned on the foreign key's cascade delete from the parent appraisal so the whole replace ran inside one transaction, with no chance of orphaned comp rows if something failed partway.

Nobody has had to touch that logic since. The honest tradeoff is this only holds while the comp count stays at 6. If we moved to selecting hundreds, the math flips and diffing becomes worth the complexity.

Explaining to non-technical people why a free lookup must never charge anyone

Product wanted the free browsing experience to feel fast and smooth, and someone suggested we simplify things by letting the free path and the paid path share more code. The pitch was it would save a week or two of engineering time. I needed to explain to people who don't write code why I didn't want to do that, and make it clear this wasn't just me being picky about architecture.

Talking about module boundaries and shared write paths wasn't going to mean anything to them, so I framed it around outcomes instead. We had around 5,000 properties that were free to report on. Everything else cost 10 credits for residential or 30 for commercial. If those two share a write path and a bug slips through at even a 0.1 percent rate, it breaks both ways. Someone viewing a free property gets credits burned for nothing. Or a report someone paid credits for gets silently overwritten by a free cache lookup. Either way that's a refund, a support contact, and a customer who now doubts every number we show them.

Then I put it as a simple comparison. One or two weeks of work now, or we permanently remove the chance of taking someone's credits by mistake. Not reduce the chance, remove it.

They agreed to keep them separate. What made it land was talking about money and trust instead of code. Said as architecture, it sounds like a preference. Said as refunds, it's a business decision.

Mashvisor API / Caching Layer

What is Mashvisor: A third-party real estate data API providing rental market analytics and investment metrics. The rentability tab displays rent estimates, cash-on-cash return, and short-term/long-term rental comps, all powered by Mashvisor. Each API call costs 2-5 cents, and the system makes about 20 parallel calls per property view. Without caching, this adds significant latency (8-12 seconds) and costs roughly $300-800 monthly. The caching layer sits between our app and Mashvisor, reducing redundant calls while managing freshness tradeoffs since different metrics (rent estimates vs comps) age at different rates.

Two parallel cache misses racing to insert the same row

I was building a caching layer over Mashvisor, the third party API behind our rentability tab. That tab shows rent estimates, cash on cash return, and short and long term rental comps when someone opens a property. Loading it fired about 20 parallel API calls. Under load testing, I started seeing intermittent constraint violation exceptions, roughly 1 to 2 percent of loads failing outright.

What was happening is two parallel calls would ask for the same neighborhood data within milliseconds of each other. Neighborhood metrics get reused across nearby properties, so this came up often. Both would miss the cache, and both would try to insert. A classic race condition. And it didn't fail just one metric, it failed the whole tab.

My first thought was a Redis distributed lock, but that puts latency on every single write to guard against a rare collision. On a pipeline already making 20 calls I didn't want that on the common path. So I let the database be the arbiter instead. The cache key already had a unique constraint, so the first insert wins and the second gets a constraint violation. I caught that as an expected signal rather than an error, then read back the row the winner had just written. The detail that mattered was running that catch in a fresh transaction, because once JPA hits a constraint violation it marks the whole transaction rollback-only, so a retry sharing it would fail too.

That 1 to 2 percent failure rate went to effectively zero, with no measurable latency on the normal path and no locking infrastructure to run.

Cutting repeat API calls down to zero

Our rentability tab was making around 20 calls to Mashvisor every time someone opened it, even if we'd pulled that exact same property minutes earlier. Each call costs 2 to 5 cents and we had a few hundred property views a day, so we were spending somewhere around $300 to $800 a month on data already sitting in our own database. It was slow too. Those 20 calls were most of the load time, so people were waiting 8 to 12 seconds before seeing any numbers.

I wanted to fix this without touching all 20 call sites individually. That's 20 chances to introduce an inconsistency and 20 places to maintain forever. All 20 funneled through one shared transport interface underneath, so I built the cache as a decorator over that single method instead. One wrapped method covered all 20 endpoints with zero changes at any call site.

The harder part was freshness, because these metrics don't age at the same rate. Rent estimates move slowly. Rental comps turn over faster. So I split it into two independent checks. One for whether we had the right id to call the endpoint at all, and separately whether the cached data for that id was still fresh. A valid id tells you nothing about whether a specific metric is stale, so combining them would make a stale record indistinguishable from a missing one.

Repeat views on fresh data dropped from 20 external calls to zero, which cut that monthly spend by 60 to 70 percent once the cache warmed up and brought tab load into the 2 to 3 second range. When one metric went stale, only that endpoint refetched instead of all 20.

My kill switch wouldn't have worked when we actually needed it

I built a kill switch for our caching layer using a config flag. The idea was if caching ever misbehaved in production we could turn it off in seconds instead of waiting on a rollback. During code review, a teammate asked me something I hadn't thought through. What happens if the caching database itself goes down, given the app still creates that DataSource at startup?

He was right, and it was a good catch. Optional at the config level didn't mean optional at the infrastructure level. The DataSource bean was being created eagerly regardless of the flag. So a bad connection string or an unreachable cache database would fail application startup entirely, even with caching switched off. Which means my supposed safety valve had a 100 percent chance of not working in exactly the scenario I built it for, because the service wouldn't even come up to honor the flag.

I fixed it with ConditionalOnProperty so the bean only gets instantiated when the flag is true. Flipping it off now genuinely removes the dependency instead of creating the connection and declining to use it.

That turned the kill switch from decorative into actually functional. In practice that's the difference between a 30 second config change and a full rollback and redeploy, which is more like 20 to 30 minutes during an incident. What I took from it is to think about failure in infrastructure I own, not just the systems I call out to.

Adding caching to 20 call sites without touching any of them

I got asked to add caching to the Mashvisor integration, which made about 20 different calls spread across several endpoint classes I hadn't written. The obvious approach was to wrap each call site. But that's 20 separate edits, 20 chances to miss one or implement it slightly differently, and 20 places someone has to remember to update later.

So before writing any caching code I spent about half a day tracing how those calls actually flowed. Turned out all 20, regardless of which endpoint class triggered them, funneled through a single shared transport interface with one method. That convergence point was the obvious place to cache, as a decorator around that one method. A decorator is invisible to callers, so nothing at any call site had to change.

I used Spring's Cacheable with a composite key builder that handled the varying parameter shapes across endpoints, so each unique call combination got its own cache bucket.

Caching shipped across all 20 endpoints with zero changes to existing endpoint classes. That meant zero regression risk in code I didn't write and no review burden on the teams that owned it. It also means any new endpoint added later inherits caching automatically instead of someone needing to remember to wire it up.

The half day of tracing is what bought all of that. If I'd started at the call sites, I'd have spent several days on a change with 20 times the surface area and worse long term maintainability.

Chat

What is Chat: A real-time messaging platform where brokers, lenders, buyers, and transaction coordinators coordinate on live real estate deals. Users can send and delete messages, attach documents, create sessions tied to transactions, and manage participants with different roles. Sessions persist full conversation history, support concurrent sends, and include features like enquiry sessions that can exist before a formal transaction starts. Performance is critical since users expect sub-second send operations, and any slowdown (30-60 seconds) breaks the core feature and kills deals.

Chat messages taking 30 to 60 seconds to send

During testing before release, something as simple as sending or deleting a chat message was taking 30 to 60 seconds. Nothing was erroring out, it was just too slow to use. Chat is how brokers, lenders and buyers coordinate on live deals, a few hundred conversations a day, so the main feature looked completely broken. It got flagged as a blocker that would have pushed the launch back at least a sprint.

Instead of guessing from reading the JPQL, I turned on Hibernate SQL logging locally and ran EXPLAIN ANALYZE against a dataset sized like UAT. Query plans look fine on small local data and fall apart as row counts grow, so testing against realistic data mattered.

That exposed redundant queries stacking up across message, attachment, session and participant lookups. A classic N+1 from lazy loaded associations. A single send was triggering 15 to 20 database round trips where 3 or 4 would do.

I combined several separate writes into single transactions, merged the redundant lookups into joined fetch queries, and reordered validation so cheap checks like authorization ran before any database call instead of after.

That brought it from 30 to 60 seconds down to 2 to 3 seconds, about a 95 percent improvement, and we shipped chat on the original date. Digging into the performance also turned up real bugs hiding behind the slowness, like a delete endpoint returning the wrong status code, which would have gone out quietly otherwise.

Reworking transactional boundaries so a partial write can't happen

In our message send flow, saving the message and updating the parent session's last message timestamp were two separate database writes. If anything failed between them, you end up with a message that exists but a session that doesn't reflect it. To the user that looks like an empty or stale conversation in their session list even though the message is sitting in the database. Every single send goes through this path, so even a 0.1 percent failure rate between those two writes means inconsistent conversations showing up daily.

I wanted both writes atomic without slowing down one of the hottest paths in the system. So I combined the insert and the session update into a single write inside one transaction boundary, which also cut it from two round trips to one.

I also added optimistic locking on the session with a version column, so two near simultaneous sends surface a conflict the caller can retry instead of one silently overwriting the other. I chose optimistic over a pessimistic row lock deliberately, because sends are frequent and short lived. Holding a row lock across the write would serialize unrelated sends to the same session, hurting throughput on a busy conversation, for a conflict that's genuinely rare.

The send path came out both faster and safer. Partial writes aren't just unlikely now, they're structurally impossible. It also closed a subtle bug where sessions showed stale last message data under concurrent sends.

Building enquiry sessions when the data model assumed a transaction always existed

We got asked to let a user start a chat with a transaction coordinator before any real estate transaction existed in the system. This mattered commercially because it's the top of the funnel, someone asking a question before they've committed to a deal, and until then we were forcing them to email instead. The problem was our entire chat data model, from session creation through attachment lookups, assumed a transaction id was always present. The requirement was one line, make chat work without a transaction, and the implications were mine to work out.

Making the column nullable was the easy part and nowhere near sufficient. A nullable column doesn't stop a join or role lookup written against the old assumption from silently returning nothing. That's worse than an error, because it looks like working code returning empty results. So I worked through every consumer one at a time. Session listing, closing, reopening, attachment lookups, roughly 8 to 10 distinct paths, fixing each place that assumed a transaction existed.

I also had to build new role resolution logic, since the existing logic derived a user's role from the transaction itself, which no longer applied. For enquiry sessions I derived it from the session's own participant records instead.

Enquiry sessions shipped working across every existing chat feature with no special case checks scattered through the codebase. What I took from it is to trace every consumer of an assumption before removing it.

Changing an endpoint's status codes without breaking existing consumers

We had an endpoint other services called that always returned a 200 regardless of what actually happened internally. So no consumer could distinguish a real failure from a success. Failures were being silently treated as successes downstream, which corrupts data in systems you don't own and surfaces weeks later as a bug nobody can explain.

My initial plan was just to start returning proper status codes. Partway through I realized the risk. Several teams consumed this endpoint, and some likely had logic built around always receiving a 200 with a specific body shape. Changing both the status code and the body would break them on deploy. My improvement would have turned into an incident across multiple teams.

So I adjusted the approach to guarantee the response body never changed shape, only the status code. I scoped a RestControllerAdvice to that one controller using assignableTypes, so consumers parsing the body kept working even if they hadn't updated their status handling yet, and no other controller's error handling was affected by the new advice bean.

We shipped accurate error signaling without a coordinated rollout across every consuming team, which would have taken weeks to even schedule. It wasn't the simpler plan I started with, but it let each team adopt proper status code handling on their own timeline instead of being forced into it by my deploy.

Notifications

What are Notifications: An asynchronous messaging system handling 164+ notification types across brokers, lenders, buyers, and transaction coordinators. Built on Azure Service Bus with command-style messaging and delivery guarantees, notifications cover events like signup, document submission, and account approval. Each notification can be delivered via Email, SMS, or In-App, with templates stored in the database (not code) and loaded into Redis at startup. Templates are edited without deploys, invalidated across all instances via Redis pub-sub, and failures are captured via Service Bus dead lettering for replay and audit.

Publishing notifications synchronously blocked message sends under broker slowness

Our notification pipeline runs on Azure Service Bus topics and handles 164 plus notification types across brokers, lenders, buyers and transaction coordinators, fanning out to Email, SMS and In-App. While building it I noticed the message send flow was calling the publish step synchronously, inline with the main request. Under load, if the broker got slow, that could add up to 30 seconds to something as simple as sending a chat message. Not everyone initially saw this as worth changing, because in normal conditions a publish returns in milliseconds and the problem is invisible.

So instead of arguing it abstractly, I laid out the failure scenario concretely. The broker doesn't have to go down for this to hurt. It just has to be briefly slow, which happens during throttling or a transient connectivity blip. In that window, the producer blocking on an ack means every chat send in the system blocks with it. So a secondary system having a routine hiccup takes down the primary feature, and a notification that would have been two seconds late instead becomes a message that appears to fail entirely.

I proposed making the publish fire and forget with Async, catching and logging failures inside the async method instead of letting them propagate to the caller.

We converted it and that coupling disappeared. Chat send latency became independent of broker health. A Service Bus hiccup now costs a slightly delayed notification instead of a 30 second hang on the core user action. The tradeoff we accepted explicitly is that a dropped publish loses that one notification, which is why the logging matters, though dead lettering covers failures once the message is actually accepted.

Fixing a bean initialization order bug affecting monitoring, not just my feature

While working on notification delivery, I noticed our APM logs had a gap right at startup. The first few seconds of every deploy were missing entirely. That had nothing to do with what I was assigned and nobody had traced it. But startup is exactly when things fail, bad config, unreachable dependencies, a failed migration. So we were blind during the highest risk window of every deploy, on every service.

I dug in and found it was a Spring bean initialization order issue. A log clearing configuration bean was running after the APM appender had already registered, wiping out its earliest output. Spring doesn't guarantee creation order beyond the dependency edges you declare explicitly, so these two unrelated beans could initialize in either order, and we'd landed on the wrong one.

The fix was small. An explicit DependsOn so the log clearing step runs before the appender registers instead of relying on implicit ordering.

The gap closed, which means startup failures became diagnosable from logs instead of needing a local reproduction. That's the difference between reading a stack trace and spending half a day reproducing a deploy time failure. It cost me maybe two hours and it wasn't my scope, but observability gaps compound quietly, and the next person hitting a startup issue would have burned far more than that.

Keeping 164+ notification templates editable without a code deploy

We had 164 plus notification types across brokers, lenders, buyers and transaction coordinators, covering everything from signup to financial document submission to account approval, each deliverable over Email, SMS or In-App. The key design decision was that none of that message content lives in code. It's all stored in the database and loaded into Redis at startup, so changing wording means a database update, not a code change.

The part I pushed on was invalidation. A teammate had the lookup on a hand rolled in-memory map that loaded once at startup with no eviction path at all. So any template edit was invisible until a full restart. Which means a one word copy fix on any of those 164 types required a deploy, turning a 30 second change into a release cycle.

Instead of arguing it as preference, I walked through the multi instance case, which is where it really falls apart. Even adding eviction, clearing the cache on the instance that received the request leaves every other instance behind the load balancer serving old copy indefinitely. So some users see the new message and some see the old one, which is worse than everyone consistently seeing stale text. I proposed Spring's Cacheable and CacheEvict with an authenticated reload endpoint that fans invalidation to all instances over Redis pub sub.

Template changes now propagate across every instance in seconds from a database edit, no deploy. We also deleted a chunk of hand written cache management in favour of framework code that's already tested.
