✅ JUnit Core Concepts

Definitions and use cases for JUnit testing.

Test Methods & Assertions

A test method is annotated with @Test and contains the logic and assertions that verify expected behavior, for example @Test void testAdd() { assertEquals(5, calculator.add(2, 3)); }. Common assertions:

  • assertEquals(expected, actual), compare values
  • assertTrue(condition) / assertFalse(condition), boolean checks
  • assertNull(object) / assertNotNull(object), null checks
  • assertThrows(Exception.class, () -> method()), exception testing

Test Lifecycle

Annotations controlling when setup and cleanup run:

  • @BeforeEach, runs before each test
  • @AfterEach, runs after each test
  • @BeforeAll, runs once before all tests, must be static
  • @AfterAll, runs once after all tests, must be static

Common pattern: @BeforeEach void setup() { db.createTables(); } paired with @AfterEach void cleanup() { db.clearData(); } to keep tests isolated from each other.

Parameterized Tests

Runs the same test logic against different input values using @ParameterizedTest, avoiding copy-pasted near-duplicate test methods:

  • @ValueSource(ints = {1, 2, 3, 4}), multiple simple inputs
  • @CsvSource({"1,1,2", "2,3,5"}), CSV-style multi-argument inputs
  • @MethodSource("testData"), pulls test data from a method
@ParameterizedTest
@ValueSource(strings = {"test@email.com", "user@domain.org"})
void testValidEmails(String email) {
    assertTrue(validator.isValid(email));
}

Mocking with Mockito

Mockito creates mock objects to isolate the unit under test from its dependencies.

  • @Mock, creates a mock object
  • @InjectMocks, injects the mocks into the class under test
@Mock PaymentService paymentService;
@InjectMocks OrderService orderService;

when(paymentService.process(any())).thenReturn(true);
verify(emailService).send("test@email.com");

Test Organization

  • @Tag("unit"), @Tag("integration"), tag tests for selective runs
  • @Suite + @SelectClasses({Test1.class, Test2.class}), group into suites
  • @SelectPackages("com.example.tests"), select by package

Exception Testing

assertThrows(IllegalArgumentException.class, () -> divide(5, 0));
assertThrows(UnauthorizedException.class, () -> deleteUser());

Integration Testing

Beyond isolated unit tests, Spring Boot provides slice tests for testing component interaction with real infrastructure:

  • @DataJpaTest, tests the repository/database layer only
  • @WebMvcTest, tests the web/controller layer only, with mocked service beans
  • @SpringBootTest, loads the full application context

Performance Testing

@Timeout(value = 5, unit = TimeUnit.SECONDS) fails a test if it takes longer than the given duration, useful for catching accidental performance regressions or hangs.

Quick Reference

class UserServiceTest {
    @BeforeEach
    void setUp() { /* setup */ }

    @Test
    void shouldCreateUser() {
        // Given
        String name = "John";
        // When
        User user = userService.create(name);
        // Then
        assertNotNull(user);
        assertEquals(name, user.getName());
    }

    @ParameterizedTest
    @ValueSource(strings = {"", " ", "null"})
    void shouldRejectInvalidNames(String invalidName) {
        assertThrows(IllegalArgumentException.class,
            () -> userService.create(invalidName));
    }
}

Maven / Gradle test commands:

# Maven
mvn test                    # Run all tests
mvn test -Dtest=UserTest    # Run specific test
mvn test -Dgroups=unit      # Run tagged tests

# Gradle
./gradlew test                 # Run all tests
./gradlew test --tests UserTest # Run specific test

From My Own Work

1. Byte-for-byte before/after comparison tests on a billing-relevant refactor

Situation: I was extracting core valuation logic out of a paid appraisal endpoint into a shared service so a new free cache flow could reuse it, and the endpoint was billing relevant.
Task: Prove the refactor didn't change the endpoint's behavior at all, not just assume it based on reading the diff.
Action: I wrote comparison tests that ran the exact same request against the old and new code paths and asserted the responses matched byte for byte, running against the real Spring context rather than a mocked service, since a mock would hide a subtle wiring bug from the extraction.
Result: The refactor shipped with real confidence the billing-relevant endpoint's behavior was completely unchanged, which a unit test on the extracted method alone wouldn't have proven.

2. @Container + @DynamicPropertySource to catch real SQL Server behavior H2 missed

Situation: Repository tests ran against in-memory H2, but I needed to verify behavior specific to real SQL Server, unique constraint upserts and cascading deletes.
Task: Get tests running against a real database engine without slowing the whole suite down per test.
Action: I declared the container as a static field annotated @Container so it starts once and is shared across the test class, and used @DynamicPropertySource to inject its connection details before the Spring context boots.
Result: The tests caught real constraint and cascade behavior H2 would have silently handled differently, which is exactly the gap Testcontainers exists to close.

3. Recognizing what a mock hides during an extraction refactor

Situation: While verifying a service extraction, the fast path would have been to unit test the extracted method in isolation with its dependencies mocked.
Task: Decide whether that isolated test actually proved the extraction was safe.
Action: I insisted the comparison tests run against the real Spring context instead, since a mock only verifies the caller's code path against an assumed interface, it wouldn't catch a subtle bug in how the extracted service itself gets wired or its dependencies injected.
Result: That distinction, unit testing logic versus integration testing wiring, is exactly the kind of gap a refactor is most likely to introduce and a pure mock-based test is least likely to catch.

4. A test gap that would have caught a missing-branch bug earlier

Situation: A payment status update defaulted to Pending regardless of whether a payment transaction id existed, a missing branch rather than a broken one, and it shipped without being caught.
Task: Identify what test coverage would have caught this before it reached production.
Action: After fixing the bug, I added a test asserting the correct status for every known payment state, not just the happy path, so a default-only implementation fails a test immediately instead of only surfacing once real paid records hit it.
Result: It reinforced testing every explicit branch a status or state machine can be in, not just the primary path, since a missing else-branch produces no compile error and no obvious symptom until real data exercises it.

5. A cache key collision test that verifies uniqueness across parameters

Situation: A cache key generator initially left out a secondary parameter some endpoints accepted, causing two different requests to collide on the same key and return wrong cached data.
Task: Prevent the same class of bug from recurring on a future endpoint with a different overlooked parameter.
Action: After rebuilding the key generator to derive keys programmatically from every parameter reaching the call, I added a test that calls the same endpoint with two different values for every documented parameter and asserts the cache keys differ.
Result: This kind of test catches a missing parameter automatically instead of relying on someone noticing wrong-looking cached data days or weeks later.
