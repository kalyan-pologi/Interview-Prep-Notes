Combined write-up covering Reidy, CashFlowMW, and ReidyAI.

Short Version (say this first)

Reidy is a real estate platform that connects brokers, lenders, transaction coordinators, and buyers around property deals, covering everything from tracking a transaction end to end, to real time communication between the parties, to automatically generating property appraisals and investment analysis reports. Since a lot of it touches paid transactions and production data other teams rely on, reliability and data correctness have been a constant theme across everything I've built there.

On the appraisal side, I designed and built a dual persistence architecture in Java and Spring Boot. The platform needed two different ways of handling appraisal data, a paid permanent history record that gets billed, and a free reusable cache for browsing that shouldn't be recomputed or recharged on every view. These two write paths could never share a code path, so I enforced that separation at the module level using two separate Spring Boot starter libraries. I also reconciled two structurally different valuation engines into a single shared schema using a normalizer, and extracted the core valuation logic into a shared service so both flows could reuse it without changing the paid endpoint's behavior at all, which I verified with before and after comparison tests since that endpoint was billing relevant.

I also built a real time chat and notifications system from scratch on Spring Boot, the data model, the messaging domain logic, and the real time transport layer, using WebSocket and Kafka, so notifications dispatched asynchronously never blocked a core action like sending a message. I owned that system end to end, including a performance investigation that brought core chat operations from 30 to 60 seconds down to under 2 to 3 seconds.

Separately, I built a caching layer over a third party real estate data API using Spring WebFlux, since a single report required around 20 outbound calls, many of them for data that gets reused across different properties. I designed it as a decorator wrapping one shared transport interface, so it covered all 20 endpoints without touching any individual call site, which cut redundant external calls down to zero for repeat property lookups.

Appraisal

This is the part of the platform that generates property appraisals, either a full residential or commercial valuation, or a quick comp based estimate. There are two ways an appraisal can get saved. If a user actually pays for a report, that result goes into a permanent history table, since it's tied to billing and needs to stay correct and auditable forever. If someone is just browsing a property for free, we still save an estimate, but into a separate cache that's meant to be temporary and reusable, not something we fully trust the way we trust the paid history.

I worked on keeping these two paths completely separate so a bug in one could never accidentally affect the other, on reconciling two different valuation engines (residential and commercial) that produce structurally different data into one shared schema, and on various data correctness issues around comps, payment status, and PDF report generation.

Background context only, below. This is the valuation logic the appraisal engines actually run under the hood, not something I owned myself, but useful if an interviewer digs into how the system actually computes a value.

Residential Engine

Reads property and MLS data from parquet datasets on Azure Data Lake. It builds a pool of comparable properties using geographic and feature filtering, radius, beds, baths, square footage, sale date, then runs a KNN (k-nearest neighbors) based comp selection on top of that pool. Once the nearest comps are picked, it applies per-feature dollar adjustments for things like beds, baths, pool, garage, fireplace, gross area, year built, and condition, so each comp's price gets adjusted toward the subject property.

The selected comps get split into an As-Is group and an ARV (after repair value) group, specifically to guarantee a real spread between the two numbers instead of them collapsing together. The final value comes from an inverse-distance-weighted average across the comps, falling back to a plain unweighted mean when there isn't enough spread in the underlying data. A rehab cost range is derived separately, from a reconstruction cost multiplied by a condition-based fraction, with a plus or minus band around it.

Commercial Engine

This one is backed by SQL instead of parquet, and it's structured as a multi-agent pipeline rather than one single calculation. Separate agents each produce one section of the appraisal: a sales approach that uses comps with percentage-based adjustments instead of dollar ones, a cost approach based on replacement cost and depreciation, and an income approach based on NOI and cap rate, which has no equivalent on the residential side at all. A reconciliation agent then takes all three outputs and combines them into one final value using weighted approach scores.

Why This Mattered for the Persistence Work

The two engines produce fundamentally different shaped output. Residential gives per-feature dollar adjustments, commercial gives percentage adjustments by category, and has no equivalent for several residential-only fields like beds or baths. Reconciling both into one shared database schema meant writing a normalizer that converts commercial's percentages into dollar amounts at write time, and deliberately leaving engine-specific columns null for whichever engine doesn't produce that field, instead of maintaining two separate table shapes for what is conceptually the same kind of record.

Mashvisor API / Caching Layer

Generating a full investment report means calling a third party real estate data provider, Mashvisor, around 20 times for things like rental estimates, neighborhood data, and comp information. A lot of that data doesn't change often, and the same property or neighborhood gets looked up again and again, so calling the API fresh every single time was slow and expensive.

I built a caching layer in front of those calls so repeat lookups could be served from our own database instead of hitting the external API again. It's designed as a decorator around one shared interface, so it covers all 20 endpoints without needing to touch each call site individually, and it tracks freshness independently per endpoint since different types of data go stale at different rates. This is also where I dealt with concurrency issues, like two parallel requests racing to cache the same property at the same time.

Chat

This is the real time messaging system that lets the different people on a deal, brokers, lenders, transaction coordinators, and buyers, communicate directly inside the platform. I built this from scratch, the data model, the messaging logic, and the real time transport layer using WebSocket.

Beyond just building the core feature, I owned it end to end in production, which meant handling performance problems as the system scaled, fixing data consistency issues around concurrent message sends, and extending the chat model to support cases the original design hadn't planned for, like letting someone message a transaction coordinator before an actual deal even existed in the system.

Notifications

Whenever something relevant happens, a new message, a status change, an update on a deal, the platform needs to notify the right people. This runs on Kafka as an event driven pipeline, so the service that triggers an event doesn't have to wait around for the notification to actually be delivered.

A lot of my work here was about making sure notifications never became a liability for the rest of the system, keeping notification delivery decoupled from core actions like sending a message so a slow notification system could never block something time sensitive, and keeping notification templates and delivery logic consistent and easy to update without needing a full redeploy.
