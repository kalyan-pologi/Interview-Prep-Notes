Kubernetes concepts and commands.

Basic info & configuration

kubectl version --short              # Show client & server versions
kubectl cluster-info                 # Show cluster details (API server, DNS, etc.)
kubectl get all                      # List all resources in current namespace
kubectl config get-contexts          # List kubeconfig contexts
kubectl config use-context <context> # Switch between clusters/contexts
kubectl config view                  # Show kubeconfig file
kubectl get ns                       # List all namespaces
kubectl create namespace <name>      # Create new namespace
kubectl delete namespace <name>      # Delete namespace and all resources

Pod management

kubectl get pods                         # List all pods in current namespace
kubectl get pods -n <namespace>          # List pods in specific namespace
kubectl describe pod <pod_name>          # Detailed pod info and events
kubectl logs <pod_name>                  # Show logs of a pod
kubectl logs -f <pod_name>               # Stream live logs (follow mode)
kubectl exec -it <pod_name> -- bash      # Open shell into pod
kubectl delete pod <pod_name>            # Delete a pod (Deployment auto-recreates)
kubectl port-forward <pod_name> 8080:80  # Map local port 8080 to pod port 80
kubectl get pod -o wide                  # Show pod IP and node info

Deployments

kubectl get deployments                  # List all deployments
kubectl describe deployment <name>       # Detailed info (strategy, events, etc.)
kubectl apply -f <file.yml>              # Create or update deployment from YAML
kubectl create -f <file.yml>             # Create resources from YAML
kubectl delete -f <file.yml>             # Delete resource(s) from YAML
kubectl rollout status deployment/<name> # Watch rollout progress
kubectl rollout history deployment/<name> # Show deployment revision history
kubectl rollout undo deployment/<name>   # Rollback to previous version
kubectl scale deployment <name> --replicas=3 # Scale up/down pods
kubectl set image deployment/<name> <container>=<image>:<tag> # Update image
kubectl get rs                           # Show ReplicaSets

Services

kubectl get svc                          # List all services
kubectl describe svc <name>              # Show details of a service
kubectl expose deployment <name> --port=80 --target-port=8080 --type=ClusterIP # Create service
kubectl get endpoints                    # Show service endpoint (pod IPs)
kubectl delete svc <name>                # Delete a service

Ingress

kubectl get ingress                      # List all ingress resources
kubectl describe ingress <name>          # Show ingress routing details
kubectl delete ingress <name>            # Delete ingress
kubectl get pods -n ingress-nginx        # Check ingress controller status
kubectl logs -n ingress-nginx <pod_name> # View ingress logs
minikube tunnel                          # Expose ingress on 127.0.0.1 (local)

ConfigMaps & secrets

kubectl get configmap                    # List config maps
kubectl describe configmap <name>        # View details
kubectl create configmap my-config --from-literal=key=value  # Create simple configmap
kubectl create configmap app-config --from-file=config.yml   # From file
kubectl delete configmap <name>          # Delete configmap
kubectl get secrets                      # List secrets
kubectl describe secret <name>           # Show details (values are base64)
kubectl create secret generic my-secret --from-literal=USER=admin --from-literal=PASS=1234
kubectl delete secret <name>             # Delete secret

Nodes & cluster

kubectl get nodes                        # List cluster nodes
kubectl describe node <name>             # Show detailed node info
kubectl cordon <node>                    # Mark node as unschedulable
kubectl drain <node>                     # Evict pods safely from node
kubectl uncordon <node>                  # Make node schedulable again

Storage

kubectl get pv                           # List persistent volumes
kubectl get pvc                          # List persistent volume claims
kubectl describe pv <name>               # Details of persistent volume
kubectl describe pvc <name>              # Details of PVC
kubectl delete pvc <name>                # Delete PVC
kubectl apply -f mysql-pv.yml            # Apply your storage config

Logs, events & debugging

kubectl logs <pod_name>                  # Get pod logs
kubectl logs -f <pod_name>               # Follow logs
kubectl describe pod <pod_name>          # View pod events & issues
kubectl get events --sort-by=.metadata.creationTimestamp # Recent cluster events
kubectl top pods                         # CPU/memory usage of pods
kubectl top nodes                        # CPU/memory usage of nodes
kubectl exec -it <pod_name> -- /bin/sh   # Exec shell in busybox/alpine pod
kubectl delete pod <pod_name> --force --grace-period=0  # Force delete stuck pod

Namespaces & contexts

kubectl config set-context --current --namespace=microservices  # Switch default namespace
kubectl get pods -n microservices                                # Use specific namespace
kubectl get all -A                                               # Everything, all namespaces

YAML exports

kubectl get pod <name> -o yaml           # Export full YAML of a pod
kubectl get deployment <name> -o yaml    # Export deployment YAML
kubectl get svc <name> -o yaml           # Export service YAML

Delete & cleanup

kubectl delete pod <name>                # Delete pod
kubectl delete deployment <name>         # Delete deployment
kubectl delete svc <name>                # Delete service
kubectl delete ingress <name>            # Delete ingress
kubectl delete all --all                 # Delete EVERYTHING in current namespace
kubectl delete -f k8s/                   # Delete all your project resources

Quick monitoring shortcuts

watch kubectl get pods                   # Watch pods status live
kubectl get pods -w                      # Watch for changes in pods
kubectl get svc,pods,deployments         # Combined quick view
kubectl get events --sort-by='.lastTimestamp' # Watch live events

Daily dev workflow

kubectl apply -f k8s/namespace.yml       # Create namespace
kubectl apply -f k8s/                    # Deploy all microservices
kubectl get pods -n microservices        # Check pods
kubectl logs -f <pod_name> -n microservices  # View live app logs
kubectl get ingress -n microservices     # Verify ingress rules
minikube tunnel                          # Enable Ingress routing (keep running)
kubectl delete -f k8s/                   # Tear down everything

From My Own Work (Docker & Kubernetes)

1. A multi-instance failure that was really an orchestration/routing problem

Situation: Our real time messaging service had intermittent connection failures under multi-instance load, root-caused to sticky session cookies not surviving a hop through our content delivery layer.
Task: Fix a problem that was fundamentally about how requests get routed across multiple running instances, not a single-instance bug.
Action: I proposed migrating to a managed relay so no client needed to stay pinned to one instance, since sticky sessions only reduce the odds of hitting the wrong instance, they don't remove the requirement for affinity in the first place.
Result: This is the same class of problem Kubernetes Services and load balancing are designed to solve architecturally, treating pods as interchangeable rather than requiring client affinity to a specific instance.

2. Why a config flag couldn't rely on the container just not calling a dependency

Situation: A cache feature's flag only gated behavior, not bean creation, so the DataSource was still built eagerly on container startup and could crash-loop the whole application on a bad connection string.
Task: Make the flag genuinely remove the dependency so a bad config value couldn't take down the container.
Action: I used @ConditionalOnProperty so the bean is only created when the flag is true, which matters specifically in a containerized deployment where a failed startup means a failed readiness probe and the orchestrator repeatedly restarting a container that will never come up healthy.
Result: It reinforced thinking about failure of infrastructure a container depends on, since a crash loop from a bad optional dependency looks identical to a real outage from the orchestrator's point of view.

3. Externalizing configuration instead of baking it into the image

Situation: Services needed different configuration (connection strings, feature flags, storage account names) across dev, UAT, and prod, and one specific bug came from a storage account name being wrong for the environment it ran in.
Task: Make configuration environment-specific without building a separate image per environment.
Action: Configuration was externalized via Spring profiles and environment variables rather than hardcoded, the same pattern Kubernetes ConfigMaps and Secrets exist to support, one image, config injected at deploy time per environment.
Result: The actual bug still came from a wrong config value, which reinforced that externalizing config solves portability, it doesn't remove the need to get the value itself right per environment.

4. Designing a service to be safely restarted or scaled without losing state

Situation: Presence tracking initially lived in one application instance's memory, which gave inconsistent results once multiple instances were running behind a load balancer.
Task: Make the service's behavior correct regardless of which instance, or how many instances, handled a given request.
Action: I moved presence into a shared Redis-backed service instead of per-instance memory, so any instance reads the same source of truth, which is exactly the statelessness assumption Kubernetes deployments and horizontal scaling depend on.
Result: A pod being killed, restarted, or scaled out should never change correctness, and this fix was what actually made that true for presence data.

5. Docker for consistent local development and CI builds

Situation: Spring Boot services needed to build and run identically across a developer's machine, CI, and deployment targets, and integration tests needed a real database rather than an approximation.
Task: Remove "works on my machine" as a category of problem for both running the service and testing it.
Action: Services were packaged as Docker images built from the same Dockerfile used in CI, and integration tests used Testcontainers to spin up a real SQL Server instance in a container rather than relying on an in-memory substitute like H2.
Result: The same containerization that makes deployment portable also made testing more honest, since the database in the test container behaved the same as the one in production.
