1. Tell me about a production bug you handled.

So one bug I ran into in production was around concurrent requests updating the same property cache record. Everything looked fine in normal testing, but under real parallel traffic, two requests could both check the database, both see the record didn't exist yet, and both try to insert it almost at the same time. That threw unique constraint errors for whichever request lost the race.

I reproduced it locally by firing concurrent calls and confirmed it really was a race condition, not just a validation bug. We fixed it by keeping the unique constraint at the database level and using a try-insert approach, so if another request had already inserted that row, we caught the conflict and just did an update instead. After that, I added tests specifically for concurrency and watched the production logs closely after deploying. That made the cache safe even when multiple requests hit the same property at once.

2. How do you debug an issue in production?

First thing I do is figure out the actual impact, which users or APIs are affected, when it started, and whether it lines up with a recent deployment. Then I go into the logs using something like a request id, user id, or transaction id so I can trace that specific request across services. I'll also check the usual metrics, response time, error rate, CPU, memory, database connections, and Kafka consumer lag if it's relevant.

Once I've narrowed down the failing component, I try to reproduce the same scenario in a lower environment with similar input, rather than poking around directly in production, since that tends to make things harder to reason about. After I've actually found the root cause, we decide whether it needs a code fix, a config change, or a rollback. And once that fix goes out, I keep watching the same logs and metrics to make sure the problem is actually gone, not just quiet for a bit.

3. Tell me about a challenging technical problem you solved.

One that stands out is reducing how many external property data calls we made in our appraisal workflow. A single report could trigger around 20 calls, and a lot of that data barely changed between calls, so recalling everything every single time was adding both latency and real API cost.

I built a caching layer around our WebClient based integration, but instead of giving the whole property record one blanket expiration time, I tracked freshness separately for each endpoint, since different pieces of data update at completely different rates. If something was still fresh, we just served it from our own database, otherwise we only refreshed that specific piece from the external service. I also had to make sure the cache held up under concurrent requests. With that design, we cut external calls for a typical report from around 20 down to about 5, without losing the freshness the business actually needed.

4. Tell me about a time you had a conflict with a teammate. How did you handle it?

I had a disagreement with another developer over how to design caching for an external API. He wanted one single TTL for the whole property record, mainly because it was simpler, and I felt different pieces of data really needed different expiration times since they updated at different rates. Instead of just going back and forth on opinions, we sat down and actually looked at the real API behavior and the business requirements together.

We compared how often each endpoint's data actually changed, what each external call cost us, and how much extra complexity the independent freshness logic would add. Based on that, we agreed to use independent freshness only where it genuinely mattered, and kept things simple everywhere else. I think disagreements like this are normal on any team, and the way through it is moving the conversation away from personal preference and toward actual data, requirements, and what's maintainable long term.

5. Tell me about a time you improved application performance.

One I'm proud of was on our chat feature. During UAT, basic things like sending or deleting a message were taking 30 to 60 seconds, which made the whole feature look completely broken, even though nothing was actually throwing errors. I had to dig into where that time was actually going, since it clearly wasn't just one slow query.

I turned on Hibernate's SQL logging locally and ran EXPLAIN ANALYZE against a dataset close to UAT size, and that showed a pattern of redundant queries piling up across message, attachment, session, and participant lookups, basically an N+1 problem from lazy loaded associations. I combined several separate writes into single transactions, merged the redundant lookups into joined queries, and moved some non critical work like Kafka publishing off the main request thread using Async.

That brought the operation down from 30 to 60 seconds to under 2 to 3 seconds. What I liked about this one is the fix came from actually profiling and understanding the query pattern, not from just throwing an index at it and hoping.

6. Tell me about a deployment that caused an issue and how you handled it.

I built Flyway migrations for a new caching schema on our appraisal service, and they worked fine in dev and UAT, so everything looked ready to ship. But when we ran the exact same migrations against a genuinely fresh, empty database, they failed with a SQL Server specific error, because the migration assumed the schema itself already existed.

Instead of just patching around it for that one environment, I added a proper baseline migration that explicitly creates the schema first, using an if-not-exists guard, and ordered it ahead of everything else by version number so Flyway itself enforced the ordering instead of relying on someone remembering a manual setup step. After that fix, migrations succeeded reliably on a completely fresh database, not just ones that already happened to have the schema from earlier testing. It was a good reminder that passing in every environment I've tested isn't the same as actually being correct.

9. How do you design a RESTful API?

When I design a REST API, I first understand the business use case and identify the main resources and operations. For example, in my recent real-estate project, we had appraisal and property resources, so I would define endpoints around those resources rather than around actions. Then I decide the request and response models, HTTP methods, status codes, validation rules, and error responses. I usually keep controllers lightweight and put the business logic in the service layer, with repositories handling database operations. I also think about security using OAuth2 or JWT, input validation, pagination, and idempotency where duplicate requests could cause problems. For external integrations, I consider timeouts, retries, circuit breakers, and caching. Once implemented, I write unit and integration tests and validate different scenarios through Postman. Finally, I add proper logging and monitoring so production issues can be traced quickly.

12. Explain your Agile/Scrum sprint flow.

We generally work in two-week sprints. Before the sprint starts, we have refinement sessions where the team reviews upcoming stories, clarifies requirements, discusses technical dependencies, and estimates the work. During sprint planning, we decide which stories we can realistically complete based on team capacity and priority. Each day we have a short stand-up where we discuss what we completed, what we're working on, and any blockers. Once I pick up a story, I develop it locally, add unit or integration tests, test the functionality, and create a pull request. After code review and approval, the changes move through our CI/CD pipeline into the appropriate environment, where QA validates them. We also track progress throughout the sprint and discuss blockers early rather than waiting until the end. At the end, we have a sprint review or demo and a retrospective to discuss what went well and what we can improve.

13. How do you handle changing requirements during a sprint?

First, I try to understand whether it is a small clarification or a significant scope change. If it's something minor that doesn't affect the estimate or design much, we can usually incorporate it into the existing story. But if the change significantly affects the API contract, database model, architecture, or amount of work, I discuss it with the product owner and team rather than silently expanding the story. We look at the priority and determine whether something else should come out of the sprint, whether the story should be split, or whether the new requirement should become a separate story for the next sprint. From the development side, I also explain the technical impact so the business understands the tradeoff. The important thing for me is to stay flexible without losing control of scope. Agile allows requirements to change, but those changes should still be visible and communicated to the whole team.

14. Explain the process from coding locally to deploying to production.

Once I understand the story, I create a feature branch and implement the change locally. I run the application and test the main scenarios, then add or update unit and integration tests. I also use Postman when I'm working with APIs. Before pushing, I make sure the build passes and there are no obvious code-quality issues. Then I push the branch and create a pull request. Another developer reviews the code, and I address any comments before it is approved and merged. From there, our CI/CD pipeline builds the application, runs automated tests and quality checks, and creates the deployment artifact or Docker image. The change is first deployed to a lower environment where QA performs validation. After approval, the same version is promoted toward production according to our release process. After deployment, we verify health checks and monitor logs, error rates, response times, and other important metrics.

15. How does your team perform code reviews?

When I finish a story, I create a pull request with a clear description of what changed, why it was needed, and anything specific the reviewer should pay attention to. During the review, we look beyond whether the code simply works. We check readability, naming, business logic, error handling, security, database impact, concurrency issues, test coverage, and whether the solution fits the existing architecture. For API changes, we also check whether the request and response contracts are consistent and backward compatible where necessary. If a reviewer leaves a comment, I either make the change or discuss it if there's a technical tradeoff. I treat code reviews as a discussion rather than just an approval process. I also review other developers' pull requests because it helps me understand other areas of the system. Once comments are resolved, tests are passing, and the required approvals are received, we merge the change.

16. How do you deploy your application?

Our deployment process is mostly automated through CI/CD rather than manually copying application files to servers. After the code is reviewed and merged, the pipeline checks out the code, builds the application, runs automated tests and code-quality checks, and then creates the deployable artifact or container image. That version is deployed first to a lower environment so we can verify the functionality and allow QA to test it. Once everything is validated and the release is approved, we promote the same tested version to production. In my recent project, our services were hosted on Azure, so after deployment I would verify that the application started correctly, health endpoints were responding, and dependent services such as the database, Kafka, Redis, and external APIs were behaving normally. I consider deployment complete only after we confirm the application is healthy and the important production metrics remain stable.

17. What do you monitor after a production deployment?

Immediately after a production deployment, I focus on the signals that can tell us quickly whether the new version introduced a problem. I first check application health and startup logs to make sure all services came up successfully. Then I monitor error rates, API response times, request volume, CPU and memory usage, and database connection behavior. If the release involves Kafka, I also watch consumer lag and processing failures. For external integrations, I check timeout and error rates because sometimes the application itself looks healthy while a dependency is failing. I also look specifically at logs related to the feature we just released instead of only watching overall system metrics. If we changed an important business workflow, we verify a few real transactions as well. We usually monitor more closely immediately after release, because catching an abnormal trend early makes troubleshooting or rollback much easier.

18. What do you do if a deployment fails?

First, I determine where the failure happened. If the CI/CD pipeline failed during the build or automated tests, I check the pipeline logs and fix the underlying code, configuration, or dependency issue before attempting another deployment. If the deployment completed but the application fails to start, I check startup logs, environment variables, configuration, database migrations, and connectivity to dependent services. If production is already affected, restoring service becomes the priority rather than debugging indefinitely in production. Depending on the issue, we either roll back to the last known stable version or fix forward if the problem is very small and the solution is clear. After service is stable, we reproduce the failure in a lower environment and identify the actual root cause. I also make sure we add a test or deployment check where possible so that the same type of failure gets caught earlier in future releases.

19. How do you rollback a production release?

I try to make rollback straightforward by treating every release as a versioned artifact rather than rebuilding old code when something goes wrong. If a new production release introduces a serious issue, we first confirm that rolling back is safe, especially if the release includes database schema changes. Then we redeploy the previously validated application or container version through the deployment pipeline. After rollback, I verify the health endpoints, logs, API error rates, response times, and the business flow that was affected to make sure the system is stable again. Database changes require more care because application rollback is easy only when schema changes are backward compatible. That's why I prefer additive database changes where possible instead of immediately removing or renaming columns. Once production is stable, we investigate the failed release separately, reproduce the problem, implement the fix, test it properly, and then schedule another deployment rather than rushing the same change back into production.
